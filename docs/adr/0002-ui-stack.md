# ADR-0002. Стек інтерфейсу користувача

**Статус:** Запропоновано
**Дата:** 2026-10-29
**Джерела:** [requirements_digest.md](../requirements_digest.md) (TA-5, TA-8, TA-12, TA-15, BR-12, FB-3, FB-12, G8, G10); [3.5](../../results/3.5_acceptance_criteria_result.md) (US-5.1-AC-03…06, US-5.3, US-A.4a-AC-01…03, US-A.4b-AC-01…03, Q05, Q13, Q14, Q15); пов'язані ADR-0001, ADR-0003, ADR-0007.

## Контекст

- Клієнт — мобільний вебзастосунок (mobile-first) у браузері телефона; нативного застосунку немає **[Факт від команди]**.
- Студент сканує статичний QR кімнати камерою в браузері (US-5.1, US-5.2, TA-12). Камера в браузері доступна лише в захищеному контексті (HTTPS або `localhost`) і після дозволу користувача; відмову в доступі треба обробити (Q15).
- Адміністратор генерує QR кімнати й друкує його із застосунку на папері (US-A.4a, US-A.4b) **[Рішення команди]**. Токен QR отримує лише адміністратор (FB-12).
- Таймер дедлайну рахується від серверного часу (TA-5, US-5.3), нагадування й повідомлення на початку бронювання — на клієнті з даних бронювання, без push (TA-8, BR-12, FB-3).
- Інтерфейс роблять троє людей з фронтенд-роллю, з них одна — UI/UX.

## Критерії

1. Низький поріг входу й підтримка ШІ-асистентом.
2. Та сама мова, що на бекенді (TypeScript, ADR-0003).
3. Мінімум налаштувань збирача.
4. Поділ екранів між людьми.

## Розглянуті варіанти

- **A. React + Vite + TypeScript** (односторінковий застосунок).
- **B. Vue + Vite + TypeScript.**
- **C. Next.js** (React з серверним рендерингом і власним серверним шаром).

| Критерій | A. React + Vite | B. Vue + Vite | C. Next.js |
| --- | --- | --- | --- |
| Поріг входу, ШІ | Найбільше прикладів і бібліотек; ШІ генерує стабільно | Простий шаблонний синтаксис, прикладів менше | Більше понять (серверні й клієнтські компоненти, маршрутизація файлами) |
| Мова | TypeScript | TypeScript | TypeScript |
| Налаштування | Шаблон Vite, проксі до API з коробки | Так само | Власний сервер, дублює роль бекенду (ADR-0003) |
| Камера й QR | Бібліотеки сканування й генерації працюють без обгорток | Так само | Камера лише в клієнтських компонентах, додаткові обмеження |
| Поділ роботи | Екран = окремий компонент і папка | Так само | Так само, але межа клієнт/сервер розмита |

## Рішення

**Варіант A: React + Vite + TypeScript** **[Пропозиція]**, односторінковий застосунок у `client/`.

- **Маршрутизація:** React Router. Окремі групи маршрутів для студента й адміністратора; приховування адмін-екранів лише зручність, доступ перевіряє сервер (ADR-0005, FB-11).
- **Звернення до API:** вбудований `fetch` через одну спільну обгортку, яка додає обробку єдиного формату помилок (4.3). Окремої бібліотеки стану немає.
- **Стилі:** CSS Modules (вбудовані у Vite), mobile-first макет **[Пропозиція]**. Бібліотеку компонентів обирає Зінченко Вероніка, якщо вона не додає налаштувань; за замовчуванням — без неї.
- **Сканування QR:** бібліотека на основі `getUserMedia`; основний кандидат — `qr-scanner`, запасний — `@zxing/browser` **[Пропозиція]**. Вбудований `BarcodeDetector` не є основним, бо підтримується не всіма мобільними браузерами. Перевірити основну бібліотеку на iOS Safari й Android Chrome до кінця першого тижня **[Потребує перевірки]**. Екран сканування обробляє: відмову в доступі до камери, невідомий QR, відповідь сервера про причину відмови (G5, Q15).
- **Генерація й друк QR:** бібліотека `qrcode` генерує зображення з токена на клієнті; друк — стандартне вікно друку браузера зі стилями для друку (`@media print`) **[Пропозиція]**. Окремої серверної операції для друку немає (TA-12). Пристрої друку — Q14, перевіряються вручну (ADR-0008).
- **Таймер:** клієнт обчислює різницю між серверним часом з відповіді й власним годинником і рахує відлік від дедлайну з відповіді (TA-5). Дедлайн клієнт не обчислює сам, тому рішення не залежить від G1.
- **Нагадування й повідомлення:** обчислюються на клієнті з даних бронювань при відкритті застосунку й періодичному оновленні списку (TA-8, BR-12). Service Worker, push і встановлення як PWA не використовуються (FB-3). Правила показу залежать від G10/Q05 і Q13 й ізолюються в одному модулі.

## Наслідки

- Простіше: один збирач для розробки й тестів (Vitest, ADR-0008); проксі Vite на `/api` дає одне походження для клієнта й API, тому не потрібні CORS і окреме HTTPS для API (ADR-0005, ADR-0007).
- Складніше: камера потребує HTTPS на телефоні (ADR-0007); поведінка бібліотеки сканування на різних браузерах — ризик, тому перевірка в перший тиждень.
- Прийнятий ризик: без push повідомлення бачить лише той, хто відкрив застосунок (TA-8) **[Рішення команди]**.
- Для 4.3: відповіді з бронюваннями містять дедлайн і серверний час (TA-5); помилки підтвердження розрізняються машинним кодом (G5).
- Для 4.4: сторінка-заглушка з назвою Roomly й назвами майбутніх екранів, що звертається до `GET /api/health`.
- Стосується: Анастасії, Вероніки, Вікторії.

## Що відхилено

- **B. Vue** — придатний, але менше прикладів і бібліотек для ШІ-асистента, перевага в простоті не переважує критерій 1.
- **C. Next.js** — має власний серверний шар, який дублює бекенд і ускладнює роботу з камерою.
- **Вбудований `BarcodeDetector` як основний спосіб сканування** — не працює в усіх мобільних браузерах.
