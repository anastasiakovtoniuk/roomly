# ADR-0004. Збереження даних

**Статус:** Запропоновано
**Дата:** 2026-10-29
**Джерела:** [requirements_digest.md](../requirements_digest.md) (розділи 2–3, BR-1, BR-9, BR-13, BR-14, TA-2, TA-3, TA-4, TA-7, TA-10, TA-11, TA-13, FB-14, G1, G2, G7); [3.5](../../results/3.5_acceptance_criteria_result.md) (SYS-AC-06, SYS-AC-08, US-3.4-AC-03, Q03, Q04, Q10); пов'язані ADR-0003, ADR-0005, ADR-0006, ADR-0007.

## Контекст

- Чотири сутності зі зв'язками «один до багатьох» (Room → Slot → Booking, User → Booking); дані реляційні за природою.
- Для одного слота не більше одного живого бронювання (BR-1), і захист має бути на рівні сховища, а не лише в коді (TA-7, SYS-AC-06, US-3.4-AC-03). Історичні бронювання слота зберігаються.
- Ідентифікатори — UUID, генерує сервер (TA-3); час — UTC (TA-4); бронювання не видаляються (TA-10).
- Адміністратор створюється seed-ом, пароль — із середовища (TA-2, FB-14, SYS-AC-08).
- Запуск 1–2 командами без платних сервісів; обсяг даних демонстраційний (TA-13).
- Набір статусів може змінитися (G2/Q03: п'ятий статус), дедлайн може залежати від моменту бронювання (G1/Q04).

## Критерії

1. Захист BR-1 засобами сховища (обов'язковий, без нього варіант відпадає).
2. Низький поріг входу й підтримка ШІ-асистентом.
3. Мінімум інфраструктури: без окремого сервера бази, якщо можна.
4. Міграції й seed, що запускаються однією командою.

## Розглянуті варіанти

СУБД:

- **A. SQLite** (файл бази в `server/`).
- **B. PostgreSQL** (окремий сервер, локально або в Docker).
- **C. MongoDB** (документоорієнтована).

| Критерій | A. SQLite | B. PostgreSQL | C. MongoDB |
| --- | --- | --- | --- |
| Захист BR-1 у сховищі | Часткове обмеження унікальності (слот, лише для живих статусів); записи серіалізуються | Часткове обмеження унікальності; повні транзакції | Частковий унікальний індекс є, але зв'язки між колекціями без зовнішніх ключів |
| Поріг входу, ШІ | Нуль установки; SQL і ORM добре відомі ШІ | Добре відомий, але потрібна установка | Добре відомий, але модель даних не пасує до зв'язків |
| Інфраструктура | Немає: файл створюється міграцією | Сервер бази або Docker на кожній машині | Сервер бази або Docker |
| Міграції й seed | Через ORM | Через ORM | Без схеми, міграції вручну |

ORM:

- **Prisma** — декларативна схема, міграції й seed вбудовані, перегляд даних у Prisma Studio; найбільше прикладів для ШІ. Часткове обмеження унікальності описується в схемі через попередню функцію `partialIndexes`.
- **Drizzle** — схема в TypeScript, часткові індекси виражаються прямо; прикладів менше.

## Рішення

**SQLite + Prisma 7.10.1** **[Пропозиція]**, версія зафіксована точно: тег `latest` у npm станом на 2026-10-29 вказує на передрелізну 8.0.0-rc. Prisma 7 працює з SQLite через адаптер `@prisma/adapter-better-sqlite3` (нативний модуль `better-sqlite3`).

**Перевірено 2026-10-29** (Windows 11, Node.js 22.20, у тимчасовому проєкті): установка без збірки з вихідного коду; часткове обмеження з `partialIndexes` генерується в міграції; перебудова таблиці бронювань під час наступної міграції створює обмеження знову; повторне `migrate dev` не бачить розбіжностей; із трьох паралельних бронювань одного слота успішне одне, після скасування слот бронюється знову; конкурентні умовні оновлення «підтвердити» й «автоскасувати» змінюють статус лише раз. Без `partialIndexes` (обмеження дописане в SQL міграції вручну) перебудова таблиці **мовчки видаляє** обмеження, тому цей спосіб заборонено. `partialIndexes` — попередня функція Prisma: при оновленні версії перевіряти, що обмеження лишається в міграціях; тест SYS-AC-06 (ADR-0008) ловить його втрату.

- **Тип СУБД:** реляційна. Зв'язки й обмеження цілісності потрібні для BR-1 і TA-10.
- **Захист від подвійного бронювання (TA-7, BR-1, SYS-AC-06):** часткове обмеження унікальності на слот бронювання серед записів у статусах «активне» й «підтверджене». Друге живе бронювання того самого слота сховище відхиляє за будь-якої паралельності; історичні (скасовані) записи не заважають. Обмеження описується в схемі Prisma (`partialIndexes`), а не дописується в SQL вручну. Зміни схеми — лише через `prisma migrate`, не `prisma db push`.
- **Переходи стану:** одним умовним оновленням «змінити статус, лише якщо поточний статус — X» (ADR-0006). Записи в SQLite серіалізуються, тому з двох конкурентних переходів виграє один.
- **Ідентифікатори (TA-3):** UUID, генерує сервер через ORM.
- **Час (TA-4):** усі моменти в UTC; часовий пояс університету лише для відображення, одне значення в конфігурації (G9).
- **Дедлайн підтвердження** зберігається в бронюванні **[Технічне припущення]**. Це працює за будь-якої відповіді на G1/Q04: при варіанті «початок + grace period» він просто обчислюється при створенні.
- **Статус** зберігається як рядкове значення з переліку в `shared/`, а не як тип СУБД. П'ятий статус (G2/Q03) додається без зміни типу в базі; обмеження унікальності BR-1 перелічує живі статуси явно.
- **Без каскадного видалення** бронювань (TA-10); видалення кімнат і слотів у MVP немає (FB-8).
- **Неперетин слотів (BR-13, G7/Q10)** перевіряється в сервісі в межах транзакції створення слота **[Пропозиція]**; сховище не забезпечує його, бо SQLite не має обмежень на перетин інтервалів. Ризик низький: слоти створює лише адміністратор.
- **Міграції:** `prisma migrate`; файли міграцій у репозиторії; при запуску застосовуються лише наявні міграції (ADR-0007).
- **Seed:** ідемпотентний скрипт створює адміністратора з пошти й пароля зі змінних середовища (TA-2); пароль у коді відсутній. Демонстраційні кімнати й слоти — окремий необов'язковий seed для демо **[Пропозиція]**, не функціонал.

## Наслідки

- Простіше: жодної установки бази; файл бази створюється першим запуском; Prisma Studio показує дані на рев'ю.
- Складніше: обмеження BR-1 спирається на попередню функцію Prisma; у файлі інструкцій для ШІ треба заборонити дописувати індекси в SQL міграцій вручну й оновлювати Prisma без перевірки.
- Прийнятий ризик: SQLite не підходить для розгортання з багатьма процесами; для локального MVP це не потрібно. Перехід на PostgreSQL можливий заміною провайдера Prisma й перевіркою SQL міграцій.
- Для 4.3: схема описує часткове обмеження BR-1, дедлайн у бронюванні, статус-рядок, UUID, час у UTC.
- Для 4.4: перша міграція з порожньою схемою або моделями 4.3; `GET /api/health` перевіряє з'єднання з базою.
- Стосується: Олександри (міграції, seed), Валентини й Вікторії (сервіси).

## Що відхилено

- **B. PostgreSQL** — потребує сервера бази або Docker на кожній із 5 машин, а перевага в паралельності на демо-обсязі не потрібна.
- **C. MongoDB** — дані реляційні; без зовнішніх ключів цілісність TA-10 і зв'язків доводиться тримати в коді.
- **Drizzle** — прямо виражає часткові індекси й використовує той самий драйвер, але має менше прикладів для ШІ; запасний варіант, якщо `partialIndexes` зламається.
- **Захист BR-1 лише перевіркою в коді** — суперечить TA-7.
