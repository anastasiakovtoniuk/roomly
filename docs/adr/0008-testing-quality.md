# ADR-0008. Тестування й якість

**Статус:** Запропоновано
**Дата:** 2026-10-29
**Джерела:** [3.5](../../results/3.5_acceptance_criteria_result.md) (SYS-AC-01…SYS-AC-10, §3.1, §3.3, US-3.4-AC-03, US-5.1-AC-03…06, US-5.6b, US-A.7, Q01, Q02, Q11, Q14, Q15, Q16); [requirements_digest.md](../requirements_digest.md) (BR-1, BR-4, BR-5, BR-6, BR-8, BR-10, BR-14, BR-15, TA-5, TA-7); пов'язані ADR-0003, ADR-0004, ADR-0005, ADR-0006, ADR-0007.

## Контекст

- За 5 тижнів неможливо автоматизувати 94 критерії й 77 сценаріїв 3.5; треба обрати ті, без яких ламається механіка продукту.
- Найдорожчі помилки: два бронювання одного слота (SYS-AC-06, US-3.4-AC-03), неправильні переходи статусів і автоскасування (SYS-AC-02…SYS-AC-05, SYS-AC-07), доступ студента до адмін-дій (SYS-AC-09), неідемпотентне підтвердження (US-5.1-AC-05, BR-10). Їх важко помітити вручну, бо вони залежать від часу й конкурентності.
- Часові випадки 3.5 §3.3 потребують керованого часу; межі вікна ще не визначені (Q01, Q02).
- Камера, друк QR і повідомлення залежать від пристроїв (Q14, Q15) і автоматизуються дорого.
- Код генерує ШІ-асистент; лінтер, форматер і перевірка типів ловлять частину його помилок автоматично.

## Критерії

1. Покриття критеріїв 3.5, порушення яких ламає механіку.
2. Низький поріг входу: той самий інструментарій, що для збирання.
3. Мінімум налаштувань і часу на підтримку тестів.
4. Тести не заважають паралельній роботі (кожен модуль тестується окремо).

## Розглянуті варіанти

- **A. Vitest для модульних і API-інтеграційних тестів сервера** (Supertest проти тестової бази SQLite) + ручний чек-лист сценаріїв 3.5 для інтерфейсу.
- **B. A + наскрізні тести в браузері** (Playwright) для Happy Path.
- **C. Виконувані Gherkin-сценарії** (Cucumber) для критеріїв 3.5.

| Критерій | A. Vitest + Supertest + чек-лист | B. + Playwright | C. Cucumber |
| --- | --- | --- | --- |
| Покриття механіки | Правила й переходи на сервері, де вони живуть | Те саме + інтерфейс | Те саме, текстом 3.5 |
| Поріг входу | Той самий інструмент, що Vite (ADR-0002) | Ще один інструмент, браузери | Шар кроків поверх тестів; багато шаблонного коду |
| Налаштування | Мінімальні | Браузери в CI, нестабільні тести | Окремий раннер і зв'язування кроків |
| Камера й друк | Вручну | Камера все одно не автоматизується | Не автоматизуються |

## Рішення

**Варіант A** **[Пропозиція]**.

**Що автоматизується (сервер, Vitest + Supertest, тестова база SQLite, створювана міграціями перед тестами):**

| Пріоритет | Критерії 3.5 | Що перевіряється |
| --- | --- | --- |
| 1 | SYS-AC-06, US-3.4-AC-01, US-3.4-AC-03 | Паралельні спроби забронювати один слот дають рівно одне живе бронювання; друге живе бронювання відхиляє саме сховище (TA-7) |
| 1 | SYS-AC-02, SYS-AC-03, SYS-AC-05, SYS-AC-07, SYS-AC-10, таблиця §3.1 | Кожен рядок таблиці переходів; автоскасування не чіпає підтверджене й скасоване; конкурентне підтвердження й автоскасування дають один кінцевий стан; звільнення слота |
| 1 | US-5.1-AC-03…06, US-5.6b, BR-4, BR-10 | Невідомий токен, кімната без бронювання, повтор підтвердження, скан після автоскасування |
| 2 | SYS-AC-08, SYS-AC-09, US-1.2-AC-03, US-A.4b-AC-03 | Seed створює адміністратора; кожна адмін-операція повертає «немає прав» для студента; реєстрація не дає адмін-прав |
| 2 | BR-6, BR-8 (US-X.1a, US-4.3) | Студент бачить і скасовує лише свої бронювання |
| 3 | Випадки 3.5 §3.3 з визначеним результатом | 14:05 і 14:14:59 приймаються, 14:16 після автоскасування відхиляється |

- **Керований час:** сервіси й функція автоскасування отримують поточний момент із підмінюваного джерела часу (ADR-0003, ADR-0006); тести задають момент явно, без очікування й без фальшивих таймерів для серверної логіки. Для таймера на клієнті — фальшиві таймери Vitest, якщо лишиться час.
- **Межові випадки з відкритими питаннями** (рівно 14:00, рівно 14:15, затримка доставки — Q01, Q02, Q16) не отримують вигаданого очікуваного результату; їх тест додається після відповіді команди.
- **Зв'язок з 3.5:** назва кожного тесту починається з ID критерію (наприклад, «SYS-AC-06») **[Пропозиція]**; пошук за ID показує покриття.
- **Клієнт:** модульні тести лише для чистих функцій з логікою (відлік таймера від серверного часу, правило показу нагадування BR-12) — пріоритет 3.

**Що лишається ручним:** сценарії 3.5 для інтерфейсу як чек-лист перед демо; сканування камерою на iOS Safari й Android Chrome (Q15), друк QR і зчитування з паперу (US-A.4b-AC-02, Q14), вигляд таймера й повідомлень (Q13, Q05). Gherkin-сценарії 3.5 не автоматизуються дослівно: вони залишаються специфікацією, а їх ключові перевірки покриті тестами з тими самими ID.

**Якість коду:**

- TypeScript у строгому режимі; перевірка типів усього репозиторію однією командою.
- ESLint (з правилами для TypeScript і React) і Prettier з однією конфігурацією в корені (ADR-0001) **[Пропозиція]**.
- Безкоштовна CI на GitHub Actions: на кожен PR — установка, лінтер, перевірка типів, тести **[Пропозиція]**. Злиття в `main` лише після зеленої перевірки й одного рев'ю.

## Наслідки

- Простіше: один тестовий інструмент на обидві частини; критичні правила перевіряються автоматично на кожен PR, зокрема код, згенерований ШІ.
- Складніше: сервіси мають брати час і доступ до бази так, щоб тести могли їх підмінити; це правило треба записати у файл інструкцій для ШІ.
- Прийнятий ризик: інтерфейс перевіряється лише вручну; помилки екранів знайдуться на демо-прогоні. Порожні прапорці 3.5 не означають проходження тестів, доки тести не написані й не запущені.
- Для 4.3: коди помилок мають бути машинно розрізнюваними, щоб тести перевіряли причину, а не текст.
- Для 4.4: каркас містить налаштований Vitest з одним тестом для `GET /api/health`, лінтер, форматер і CI.
- Стосується: усіх; Олександра налаштовує CI, автори модулів пишуть тести своїх правил.

## Що відхилено

- **B. Playwright** — ще один інструмент і нестабільні тести в CI, а головний ризиковий сценарій (камера) він не покриває.
- **C. Cucumber** — шар зв'язування кроків подвоює роботу без додаткового покриття; ID критеріїв у назвах тестів дають той самий зв'язок із 3.5.
- **Jest** — потребує окремого налаштування TypeScript і ESM, тоді як Vitest працює з конфігурацією Vite.
