# ADR-0005. Автентифікація й авторизація за роллю

**Статус:** Запропоновано
**Дата:** 2026-10-29
**Джерела:** [requirements_digest.md](../requirements_digest.md) (TA-1, TA-2, TA-12, TA-14, BR-8, BR-14, BR-15, BR-17, FB-5, FB-11, FB-14); [3.5](../../results/3.5_acceptance_criteria_result.md) (US-1.2-AC-03, US-X.1a, US-X.1b, US-A.4b-AC-03, SYS-AC-08, SYS-AC-09, Q08); пов'язані ADR-0002, ADR-0003, ADR-0004.

## Контекст

- Реєстрація (ім'я, пошта, пароль), вхід, вихід; пароль лише хешем; строк дії й оновлення сесії не вимагаються (TA-1).
- Дві ролі; реєстрація створює лише студента (BR-14, US-1.2-AC-03); адміністратор — seed (TA-2, FB-14).
- Ролі й ідентифікатор користувача не можна брати із запиту (BR-15, BR-17, FB-11); студентська роль не має доступу до адмін-дій (SYS-AC-09).
- Вихід має робити бронювання недоступними на пристрої без повторного входу (US-X.1b).
- Сканування QR вимагає авторизованої сесії (TA-12).
- Без SSO, підтвердження пошти й відновлення пароля (FB-5).

## Критерії

1. Безпечність за замовчуванням без глибоких знань (поріг входу, підтримка ШІ).
2. Мінімум налаштувань і секретів.
3. Справжній вихід (US-X.1b) і перевірка ролі на сервері.
4. Сумісність з одним походженням клієнта й API (ADR-0002, ADR-0007).

## Розглянуті варіанти

- **A. Серверна сесія:** випадковий непрозорий токен у cookie `HttpOnly`, `SameSite=Lax`; сесії зберігаються в базі.
- **B. JWT у cookie `HttpOnly`** без зберігання на сервері.
- **C. JWT у `localStorage`**, передається в заголовку запиту.

| Критерій | A. Сесія в базі | B. JWT у cookie | C. JWT у localStorage |
| --- | --- | --- | --- |
| Безпечність за замовчуванням | Токен недоступний JavaScript; роль читається з бази | Токен недоступний JavaScript; роль у токені | Токен доступний будь-якому скрипту на сторінці |
| Налаштування, секрети | Без секретного ключа; одна додаткова сутність у базі | Секретний ключ у середовищі | Секретний ключ; клієнт керує заголовками |
| Вихід (US-X.1b) | Сесія видаляється на сервері, токен більше не дійсний | Видаляється лише cookie; токен лишається дійсним | Видаляється на клієнті; токен лишається дійсним |
| Одне походження | Cookie працює без CORS | Так само | Не залежить, але потребує коду на клієнті |

## Рішення

**Варіант A: серверна сесія в базі** **[Пропозиція]**.

- Після входу сервер створює сесію з випадковим токеном і ставить його в cookie `HttpOnly`, `SameSite=Lax`, `Secure` при HTTPS. Вихід видаляє сесію й cookie. Строку дії немає (TA-1); за потреби його легко додати.
- На кожен захищений запит проміжний обробник знаходить сесію й користувача в базі; ідентифікатор і роль беруться звідти (BR-17, FB-11), а не з тіла чи параметрів запиту.
- Окремий проміжний обробник ролі закриває всі адміністративні маршрути (BR-15, SYS-AC-09), включно з видачею токена QR (FB-12, US-A.4b-AC-03). Видимість бронювань (BR-8) перевіряється в сервісах.
- Хешування пароля: bcrypt через `bcryptjs` (чистий JavaScript, без нативної збірки на Windows) **[Пропозиція]**.
- Реєстрація завжди створює роль «студент»; роль у запиті ігнорується (BR-14). Пошта нормалізується до нижнього регістру й унікальна (BR-14). Мінімальна довжина пароля 8 символів — **[Технічне припущення]** TA-14, відкрите в 3.5 Q08; правило лежить у схемі валідації в `shared/` і змінюється в одному місці.
- Адміністратор створюється seed-ом (ADR-0004) з пошти й пароля зі змінних середовища.
- Захист від CSRF: `SameSite=Lax` і лише JSON-запити для змін **[Технічне припущення]**; окремі CSRF-токени не вводяться, бо клієнт і API на одному походженні.

## Наслідки

- Простіше: немає секретного ключа для підпису; вихід справжній; зміна ролі в базі діє одразу.
- Складніше: кожен запит читає сесію з бази (на демо-обсязі непомітно); сесія — додаткова технічна сутність, яку треба описати в 4.3.
- Прийнятий ризик: без строку дії сесія живе до виходу (TA-1). Без обмеження спроб входу — демо-рівень **[Технічне припущення]**.
- Для 4.3: операції реєстрації, входу, виходу й отримання поточного користувача; коди помилок «не автентифіковано» й «немає прав» у єдиному форматі.
- Для 4.4: каркас не містить автентифікації, лише місце для проміжних обробників.
- Стосується: Валентини (сервер), Анастасії (екрани входу й реєстрації).

## Що відхилено

- **B. JWT у cookie** — вихід не робить токен недійсним, а роль у токені не оновлюється без додаткових механізмів.
- **C. JWT у localStorage** — токен доступний скриптам на сторінці, вихід лише на клієнті.
- **Готові сервіси автентифікації** (Auth0, Firebase Auth, Clerk) — зовнішня залежність, обмеження безкоштовних планів і надлишкові функції (SSO, підтвердження пошти), які заборонені FB-5.
