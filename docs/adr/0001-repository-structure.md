# ADR-0001. Структура репозиторію

**Статус:** Запропоновано
**Дата:** 2026-10-29
**Джерела:** [requirements_digest.md](../requirements_digest.md) (TA-15), [project_context.md](../project_context.md) («Обмеження команди»), [prompts/4.2_adr_generation.md](../../prompts/4.2_adr_generation.md); пов'язані ADR-0002, ADR-0003, ADR-0007.

## Контекст

- Команда з 5 людей **[Факт від команди]** паралельно працює над клієнтом і сервером, дедлайн 4 грудня 2026 р. **[Факт від команди]**. Конфлікти злиття в спільних файлах коштують часу, якого немає.
- Клієнт і сервер мають спільні контракти (крок 4.3): статуси бронювання, правила валідації, формат помилок. Якщо їх описано двічі, вони розійдуться.
- Проєкт має запускатися 1–2 командами з кореневого `README.md`. Файл інструкцій для ШІ лежить у корені й має бачити весь код і `docs/`.
- Документація процесу (`docs/`, `prompts/`, `results/`) уже існує в корені й має лишитися поруч із кодом, щоб ШІ-асистент перевіряв контракти.

## Критерії

1. Низький поріг входу й підтримка ШІ-асистентом.
2. Одна мова й один набір інструментів.
3. Мінімум налаштувань.
4. Поділ роботи на 5 людей без конфліктів.

## Розглянуті варіанти

- **A. Монорепозиторій із npm workspaces:** `client/`, `server/`, `shared/` у корені, один `package.json` у корені зі скриптами запуску.
- **B. Монорепозиторій без workspaces:** дві незалежні папки `client/` і `server/`, кожна зі своїми залежностями; спільний код копіюється або не виноситься.
- **C. Окремі репозиторії** для клієнта й сервера, документація в одному з них.

| Критерій | A. Монорепо + workspaces | B. Монорепо, дві папки | C. Окремі репозиторії |
| --- | --- | --- | --- |
| Поріг входу, ШІ | Один клон, одна установка; ШІ бачить увесь код і `docs/` | Один клон, дві установки | Два клони; ШІ в кожному бачить лише половину контрактів |
| Одна мова, спільні типи | Спільний пакет `shared/` для статусів і схем валідації | Спільних типів немає, дублювання | Спільних типів немає або окремий пакет з публікацією |
| Налаштування | Workspaces вбудовані в npm, без додаткових інструментів | Найменше, але запуск двох процесів вручну | Два набори CI, синхронізація версій |
| Запуск 1–2 командами | Так, з кореня | Потрібен кореневий скрипт, що заходить у дві папки | Ні |
| Поділ роботи | Папки за зонами, одна гілка `main` | Так само | Добрий поділ, але зміни контракту — два PR |

## Рішення

**Варіант A** **[Пропозиція]**: один репозиторій, npm workspaces, три пакети:

- `client/` — мобільний вебзастосунок (ADR-0002);
- `server/` — API, фонове автоскасування, міграції й seed (ADR-0003, ADR-0004, ADR-0006);
- `shared/` — те, що мусить збігатися на обох сторонах: перелік статусів бронювання, схеми валідації вводу, коди помилок (зміст визначається в 4.3).

У корені лишаються `docs/` (разом з `docs/adr/`), `prompts/`, `results/`, `README.md`, файл інструкцій для ШІ, спільні конфігурації лінтера й форматера (ADR-0008) і `.env.example` (ADR-0007). Інструменти для монорепозиторіїв (Turborepo, Nx) не використовуються.

**Поділ на зони** **[Пропозиція]**: всередині `client/` і `server/` код групується за функціональними модулями (автентифікація, кімнати й слоти, бронювання, підтвердження, адміністрування), а не за технічними шарами. Тоді кожна людина працює переважно у своїх папках:

| Зона | Відповідальна | Основні папки |
| --- | --- | --- |
| Каркас клієнта, навігація, екрани студента (пошук, бронювання, мої бронювання) | Ковтонюк Анастасія | `client/` |
| UI-компоненти й стилі, адмін-екрани, друк QR | Зінченко Вероніка | `client/` |
| Наскрізна механіка підтвердження: екран сканування й модуль бронювань на сервері | Рахманова Вікторія | `client/`, `server/` |
| Автентифікація, ролі, кімнати й слоти на сервері | Дерменжи Валентина | `server/` |
| База, міграції, seed, автоскасування, локальне середовище, CI | Малій Олександра | `server/`, корінь |

`shared/` змінюється лише через PR з рев'ю від представника клієнта й сервера, бо це контракт.

## Наслідки

- Простіше: один клон і одна установка; ШІ-асистент читає контракти в `docs/` і `shared/` в одному контексті; зміна контракту — один PR.
- Складніше: треба один раз налаштувати workspaces і посилання з `client/` та `server/` на `shared/`; корінь із `package.json` і lock-файлом стає точкою можливих конфліктів (змінює лише Олександра або через PR).
- Ризик: модулі, що перетинаються (бронювання й підтвердження), можуть зачіпати одні файли. Пом'якшення: окремі гілки на історію й короткі PR.
- Для 4.3: статуси, схеми вводу й коди помилок проєктуються з розрахунком на розміщення в `shared/`.
- Для 4.4: каркас створює три пакети й кореневі скрипти.

## Що відхилено

- **B** — без спільного пакета статуси й валідація дублюються на клієнті й сервері, а запуск з кореня все одно потребує кореневого скрипта.
- **C** — два репозиторії подвоюють налаштування й розривають контракти, які ШІ-асистент має бачити разом.
