# Схема збереження даних Roomly (MVP)

**Дата:** 2026-10-30
**Джерела:** `docs/requirements_digest.md` (§2–§8: сутності, життєвий цикл, BR, FB, TA, G); `docs/adr/0004-data-storage.md`, `0005`, `0006`; `results/3.5_acceptance_criteria_result.md` (§2, SYS-AC-01…10, §3.1, §3.3, Q01…Q18); `docs/project_digest.md` (§5, §6, §9). Пов'язані контракти: [api_spec.md](api_spec.md), [error_format.md](error_format.md). Промпт: [prompts/4.3_technical_contracts.md](../../prompts/4.3_technical_contracts.md).

СУБД — SQLite, ORM — Prisma 7.10.1 (ADR-0004). Тут лише контракт: файл `schema.prisma` створюється на кроці 4.4 й реалізації історій за цим документом.

## 1. Загальні правила

- **Таблиці:** 5 — `User`, `Room`, `Slot`, `Booking`, `Session`. Інших таблиць MVP не потребує: обладнання зберігається в `Room` (§3.2), сповіщення похідні на клієнті (TA-8), доступність слота похідна (TA-11).
- **Первинні ключі:** `id String` з UUID, генерує сервер через ORM; клієнт ідентифікаторів не створює (TA-3).
- **Час:** `DateTime`, усі моменти в UTC (TA-4). «Дата» слота — похідна від `startsAt` у часовому поясі університету з конфігурації (`Europe/Kyiv` **[Гіпотеза]**, G9).
- **Видалення:** у MVP немає видалення користувачів, кімнат, слотів і бронювань (TA-10, FB-8). Усі зовнішні ключі — `onDelete: Restrict`; каскадного видалення немає **[Пропозиція]**.
- **Назви:** моделі `PascalCase`, поля `camelCase`; ті самі назви в API ([api_spec.md](api_spec.md)).
- **Зміни схеми** — лише `prisma migrate`, не `prisma db push` (ADR-0004).

## 2. Перелік значень

Значення лежать у `shared/` і є єдиним джерелом для сервера, клієнта й тестів. У базі вони зберігаються як `String`, а не як enum СУБД (ADR-0004).

### 2.1. Статус бронювання — `BookingStatus`

| Значення | Назва українською | Кінцевий? |
| --- | --- | --- |
| `active` | активне | ні (початковий) |
| `confirmed` | підтверджене | так (BR-9) |
| `cancelled_by_student` | скасоване студентом | так |
| `auto_cancelled` | автоскасоване | так |

Чотири статуси — **[Рішення команди]**, машинні значення — **[Пропозиція]**. «Живі» статуси, що утримують слот: `active`, `confirmed` (BR-1). Статус після скасування адміністратором — відкрите G2/Q03, див. §4.3.

### 2.2. Роль користувача — `UserRole`

| Значення | Назва українською |
| --- | --- |
| `student` | студент |
| `admin` | адміністратор |

Ролі — TA-2; машинні значення — **[Пропозиція]**.

| Критерій | Окрема таблиця `RoomEquipment` | JSON-рядок у `Room.equipment` |
| --- | --- | --- |
| Фільтр за обладнанням | Простий SQL-запит | Незручний, але фільтри — Post-MVP (FB-15) |
| Читання й запис кімнати | Два запити або `include`, заміна набору при редагуванні | Одне поле; заміна набору — одне присвоєння |

Сервер валідує масив схемою Zod перед записом і розбирає його при читанні; в API поле завжди `string[]`. Порожній перелік дозволено **[Пропозиція]**, Q09.

**Токен QR** генерується під час створення кімнати й ніколи не змінюється (статичний QR **[Гіпотеза]**; перевипуск — Post-MVP, FB-13). «Генерація QR» у US-A.4a — це побудова зображення з токена на клієнті. Тому повторна генерація (Q15) завжди дає той самий код. Токен віддається лише ендпоінтом адміністратора (FB-12). QR містить лише токен, без адреси застосунку **[Пропозиція]** (4.3, рішення щодо тунелю ADR-0007).

### 3.4. `Booking`

| Поле | Тип | Обов'язкове | Обмеження / значення за замовчуванням | Призначення | Джерело |
| --- | --- | --- | --- | --- | --- |
| `id` | String | так | PK, UUID | Ідентифікатор | TA-3 |
| `userId` | String | так | FK → `User.id`, `onDelete: Restrict`; береться із сесії | Студент-власник | BR-17, US-3.1-AC-02 |
| `slotId` | String | так | FK → `Slot.id`, `onDelete: Restrict` | Заброньований слот (рівно один, BR-2) | US-3.1, BR-2 |
| `status` | String | так | Значення з §2.1; за замовчуванням `active` | Стан життєвого циклу | digest §3, SYS-AC-04 |
| `deadline` | DateTime | так | UTC; обчислюється сервером при створенні й не змінюється | Дедлайн підтвердження | BR-3, TA-5, ADR-0004, US-3.2b |
| `createdAt` | DateTime | так | `now()` | Час створення | digest §2 |
| `confirmedAt` | DateTime | ні | Заповнюється разом із переходом у `confirmed` | Коли підтверджено | digest §2, US-5.1, US-A.7 |
| `confirmedById` | String | ні | FK → `User.id`, `onDelete: Restrict`; заповнюється разом із `confirmedAt` | Хто підтвердив; роль цього користувача показує «студент чи адміністратор» | digest §2, US-5.2-AC-04, US-A.7 |
| `cancelledAt` | DateTime | ні | Заповнюється при переході в будь-який статус скасування | Коли скасовано; хто — видно зі статусу | digest §2, US-4.3, US-X.3, US-A.6 |

**Дедлайн.** Для бронювання до початку слота `deadline = slot.startsAt + grace period` (BR-3, 15 хв **[Гіпотеза]**). Для слота, що вже почався, правило визначає G1/Q04; обчислення зосереджене в одній функції сервісу, а схема від відповіді не залежить, бо дедлайн зберігається (ADR-0004).

**Чого в `Booking` немає навмисно.** Власних `startsAt`/`endsAt`: бронювання триває стільки, скільки слот (BR-2). Якщо Q04 вирішить, що бронювання залишку слота має інший початок, ці поля додаються міграцією. Поля «хто скасував» і «причина»: за G2 варіант (б) їх замінює статус; за варіантами (а) або (в) знадобиться `cancelledById` або поле причини (§4.3).

| Таблиця | Поля | Тип | Джерело |
| --- | --- | --- | --- |
| `User` | `email` (нормалізована) | `@unique` | BR-14 |

### 4.3. BR-1: один живий запис на слот

**Основний варіант (ADR-0004).** Часткове унікальне обмеження на `Booking.slotId` з умовою `status IN ('active', 'confirmed')`, описане в схемі Prisma через `partialIndexes`, а не дописане в SQL міграції вручну. Сховище відхиляє друге живе бронювання слота за будь-якої паралельності; скасовані записи не заважають новим. Сервіс створення бронювання перетворює порушення цього обмеження на `409 SLOT_ALREADY_BOOKED` ([error_format.md](error_format.md)); попередня перевірка вільності в сервісі — лише для зручного повідомлення, а не захист. Втрату обмеження ловить тест SYS-AC-06 (ADR-0008).

Якщо команда за G2 введе п'ятий статус, він не входить до умови (скасування звільняє слот). Умова перелічує живі статуси явно, тож новий статус її не змінює.

**Запасний варіант** — якщо `partialIndexes` перестане генерувати обмеження після оновлення Prisma. До `Booking` додається необов'язкове поле `liveSlotId String? @unique`. SQLite допускає кілька `NULL` в унікальному стовпці, тому обмеження діє лише на живі записи. Правила для кожного переходу:

| Перехід | Що робити з `liveSlotId` |
| --- | --- |
| Створення (`active`) | `liveSlotId = slotId` у тому самому `INSERT` |
| `active` → `confirmed` (QR чи адміністратор) | Не змінювати: підтверджене утримує слот |
| `active` → `cancelled_by_student` | `liveSlotId = NULL` у тому самому умовному оновленні |
| `active` → `auto_cancelled` (масове оновлення ADR-0006) | `liveSlotId = NULL` у тому самому масовому оновленні |
| Скасування адміністратором (G2/Q03, Q18) | `liveSlotId = NULL` у тому самому умовному оновленні, незалежно від вихідного статусу |

Перехід на запасний варіант — окрема міграція, що заповнює `liveSlotId` для наявних живих записів, і рев'ю всіх місць, які змінюють `status`.

### 4.4. Правила, яких сховище не забезпечує

Перевіряються в сервісі створення слота в межах однієї транзакції (ADR-0004):

- **Початок раніше за завершення:** `endsAt > startsAt` (BR-13) → `400 VALIDATION_ERROR`.
- **Неперетин слотів кімнати:** новий слот не перетинає жоден наявний слот тієї самої кімнати: `new.startsAt < old.endsAt AND old.startsAt < new.endsAt` (BR-13) → `409 SLOT_OVERLAP`. Суміжні інтервали (кінець одного = початок іншого) не вважаються перетином **[Пропозиція]**, Q10.
- Межі тривалості, крок, створення слота в минулому й перетин опівночі — G7/Q10. До рішення: початок і завершення в межах однієї дати університету **[Пропозиція]** (G7), слот, що вже завершився, створити не можна **[Пропозиція]**.

## 5. Похідні дані

- **Вільний слот (TA-11):** немає бронювання в статусах `active`/`confirmed` і `endsAt > now` (BR-11). За G1 варіант (а) додатково `startsAt > now`.
- **Звільнений автоскасуванням (G8, US-2.6):** вільний слот, у якого є хоча б одне бронювання `auto_cancelled`. Повертається прапорцем у списку вільних слотів ([api_spec.md](api_spec.md)).
- **Прострочене активне бронювання (ADR-0006):** `status = 'active' AND deadline < now`. Межа «рівно на дедлайні» — Q01; умова зосереджена в одній функції.
- **Хто підтвердив:** `confirmedById` → роль користувача: `student` (QR) чи `admin` (ручне).

## 8. Seed

- **Обов'язковий, ідемпотентний (TA-2, SYS-AC-08):** створює адміністратора з пошти й пароля зі змінних середовища (`ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_NAME` **[Пропозиція]** щодо назв). Якщо користувач із цією поштою вже існує, seed його не змінює. Пароля в коді немає; без змінних seed завершується помилкою з поясненням.
- **Демо-дані — окремий необов'язковий seed** **[Пропозиція]**: кімнати й слоти на найближчі дні. Слоти й бронювання створюються **відносно поточного моменту** запуску, інакше ліниве автоскасування (ADR-0006) після перезапуску сервера скасує бронювання з минулим дедлайном. Демо-seed не запускається автоматично з `npm run dev`.

## 9. Залежності від відкритих питань

| Питання | Що в схемі від нього залежить | Що зміниться |
| --- | --- | --- |
| G1/Q04 | Обчислення `deadline` для розпочатого слота; умова «вільний» | Лише функція сервісу; за варіантом із новим початком — поле `Booking.startsAt` |
| G2/Q03, Q18 | Статус після скасування адміністратором | Нове значення в `BookingStatus` (§2.1) або поле причини; обмеження BR-1 не змінюється |
| G4/Q01 | Межі вікна підтвердження й прострочення | Лише функція перевірки вікна |
| G7/Q10 | Правила тривалості, суміжності й дати слота | Лише валідація в сервісі й схемі Zod |
| G9 | Часовий пояс для «дати» слота | Значення в конфігурації |
| Q08 | Обов'язковість `name`, правила пароля | Лише схеми Zod |
| Q09 | Межі `capacity`, `floor`, унікальність `name`, порожнє обладнання | Схеми Zod; за унікальністю назви — `@unique` і новий код помилки |
