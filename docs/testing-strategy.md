# Тестова стратегія Roomly

**Статус:** робочий документ issue #47. Спирається на ADR-0008 «Тестування й якість», який має статус **«Запропоновано»**, а не «Прийнято». Описано фактичний стан гілки `feature/checkin-admin`. Те, чого ще немає, позначено «заплановано» з номером issue. Кількість тестів і матриця «AC → тест» — у [testing-report.md](testing-report.md) (#54).

## 2. Рівні й інструменти

| Рівень | Інструмент | Де | Для чого |
| --- | --- | --- | --- |
| **Інтеграційний API (основний)** | Vitest 5 + Supertest проти `createApp()` і реальної SQLite | `server/test/*.test.ts` | Ендпоінт → сервіс → Prisma → БД: статус-код, `error.code`, стан у БД |
| Модульний (сервер) | Vitest | там само | Чисті функції: `checkInWindow`, `computeDeadline`, `localDate`, схеми `shared/` |
| Модульний (клієнт) | Vitest, середовище `node` | `client/src/**/*.test.ts` | Відлік, логіка check-in, `http.ts`, тексти помилок, дата й час |
| Компонентний (клієнт) | Vitest + jsdom + Testing Library (рядок `// @vitest-environment jsdom`) | `client/src/**/*.test.tsx` | Лише компоненти з логікою стану: `CheckInPage`, `BookingsPage`, `BookingCheckInPrompt`, `AuthRoute` (залежності — рішення 8, #48) |
| E2E | — | — | Не використовуємо (ADR-0008: Playwright відхилено) |

**Що мокаємо.** На сервері **Prisma й БД не мокаються ніколи**: обмеження BR-1 і умовні оновлення перевіряються справжньою SQLite. Час підмінюється через `setClock` / `useClock` (`server/src/lib/clock.ts`, `server/test/helpers/time.ts`). Єдині інші підміни на сервері: фальшивий `setInterval` і шпигун на `console.error` у тесті самого планувальника (`autoCancel.test.ts`). На клієнті сервера немає, тому мокаються межі середовища: `fetch` (`vi.stubGlobal`), `navigator.onLine`, годинник і хук `useAuth` в `AuthRoute.test.tsx`.

## 3. Організація

- **Сервер:** `server/test/<модуль>.test.ts`, один файл на модуль або тему: `auth`, `rooms`, `bookings`, `bookings.read-cancel`, `autoCancel`, `checkIns`, `adminRooms`, `adminBookings`, `schemas`, `validate`, `health`, `persistence`, `seedDemo`, `factories`.
- **AC-набори:** `server/test/<область>.ac.test.ts` — тести, виведені з вимог незалежно від автора коду. Є `admin.ac.test.ts` (#51); набори для check-in і автоскасування заплановані (#50).
- **Хелпери** (`server/test/helpers/`, #48): `factories.ts` (`createRoom`, `createSlot`, `createUser`, `createBookingRow`), `auth.ts` (`registerStudent`, `adminSession`, `sessionCookieFrom`), `time.ts` (`useClock`, `at`, `MINUTE_MS`, `HOUR_MS`).
- **Клієнт:** `client/src/**/*.test.ts(x)` поруч із модулем; конфігурація — `client/vitest.config.ts` (пояс `Europe/Kyiv` як константа збірки).
- **Іменування:** назва тесту починається з ID критерію, далі очікувана поведінка: `'US-A.7-AC-03: скасоване студентом — 409 BOOKING_STATUS_CONFLICT…'`. Для правил без AC — ID правила або питання (`FB-12`, `SYS-AC-07`, `Q10`). Пошук за ID показує покриття.
- **Запуск:** `npm test` з кореня запускає `vitest run` у `server` і `client` (`npm run test --workspaces --if-present`; у `shared` скрипта немає). CI (`.github/workflows/ci.yml`) на кожен PR виконує `lint`, `format:check`, `typecheck`, `test`, `build -w client`.

## 4. Дані й ізоляція (як у коді)

- `server/test/globalSetup.ts` видаляє `prisma/test.db` і застосовує наявні міграції (`prisma migrate deploy`) перед кожним запуском. Робоча `dev.db` не зачіпається: `DATABASE_URL` задає `server/vitest.config.ts`.
- База **спільна для всіх файлів і між тестами не очищується**. Кожен тест створює власні кімнату, слоти й користувачів (`randomUUID` у назвах, пошті й `qrToken`) і перевіряє лише свої записи: фільтр за id, а не загальні лічильники.
- `fileParallelism: false`: ліниве автоскасування глобальне, тож запит із підміненим годинником в одному файлі скасував би чужі `active` в іншому. Тести всередині файла послідовні.
- Годинник: `useClock(initial)` ставить момент перед кожним тестом і викликає `resetClock()` після нього. `APP_TIMEZONE=Europe/Kyiv` фіксований у конфігурації.
- Планувальник автоскасування не стартує з `createApp()` (лише з `server/src/index.ts`), тож у тестах таймерів немає. Тести викликають `cancelExpiredBookings(at)` напряму, а сам `startAutoCancelScheduler` перевіряють із фальшивим `setInterval`.
- Конкурентність — `Promise.all` / `Promise.allSettled` викликів **сервісу** на реальній БД. Паралельні HTTP-запити через Supertest проходять і без транзакції, тому для гонок їх недостатньо.

## 5. Правила для тестів, згенерованих ШІ

1. Тест виводиться з AC/Gherkin ([requirements.md](requirements.md) §4, [results/3.5](../results/3.5_acceptance_criteria_result.md)) і контрактів, а не з коду. Перелік «AC → тест» складається до читання реалізації (так зроблено в #51, #52).
2. Для кожного критерію є і успіх, і відмова або межа. Перевіряється HTTP-статус, `error.code` (і `details`, якщо їх вимагає контракт) **і** стан у БД.
3. Відкриті питання не фіксуються очікуваним результатом. Зокрема, рівно на `startsAt` і рівно на `deadline` тестів немає: рішення 4 `checkin_admin_flow.md` забороняє фіксувати межі, тому перевіряється час строго до й строго після. Так само без тестів статус адмін-скасування (Q03/Q18) і рівно 24 год нагадування (Q05/G10).
4. «Зламай код навмисно»: тимчасово зіпсувати умову (прибрати перевірку ролі, `<` → `<=`, прибрати транзакцію чи умову статусу), переконатися, що хоч один тест червоніє, повернути код. Таблиця «мутація → тест» — в описі PR і в секції промптів автора.
5. Заборонено: слабкі умови (`toBeDefined`, `status < 500`, «лише 200»), моки Prisma й БД, зайві моки, послаблення чи видалення наявних тестів заради зеленого результату (`AGENTS.md` §7).

## 6. Що тести не покривають і чому

| Що | Причина |
| --- | --- |
| Межі рівно `startsAt` / рівно `deadline` (Q01) | Рішення 4: межі не фіксуються тестами, хоча поведінку визначено |
| Адмін-скасування US-A.6, статус `cancelled_by_admin` (G2/Q03, Q18) | Поза обсягом сценарію (рішення 3) |
| Рівно 24 год до нагадування (Q05/G10), формат відліку (Q13) | Робочі рішення H02 і #44 не закривають питання |
| Втрата відповіді після можливого збереження (Q11) | Тести (`client/src/lib/adminBookings.test.ts`, `api/errorMessages.test.ts`) перевіряють лише, що клієнт не показує успіх і перечитує стан; цільову поведінку команда ще не визначила |
| US-2.6 «звільнені автоскасуванням» | Не реалізується за Q04 (а), рішення 2 |
| Камера, друк, реальний таймер, верстка | Залежать від пристрою; smoke-чекліст #53 |

## 7. Розбіжності між джерелами й кодом

- **Issue #47 проти коду:** issue пише, що клієнтська логіка «тимчасово тестується в `server/test/client*.test.ts`». Таких файлів немає: після #48 тести клієнта лежать у `client/src/**` і запускаються власним `client/vitest.config.ts` через кореневий `npm test`.
- **ADR-0008 проти коду:** ADR обмежує клієнт «модульними тестами лише для чистих функцій». Фактично є й компонентні тести (jsdom + Testing Library), додані за рішенням 8 сценарію. ADR не оновлено, він лишається «Запропоновано».
- **US-A.5-AC-03:** `testing-report.md` (#51) вважає критерій лише ручним (SM-01), бо тест «у списку лише записи з БД» перевіряє інше твердження. Проте в `adminBookings.test.ts` (#42) саме такий тест названо `US-A.5-AC-03`. Команді треба вирішити: перейменувати тест (наприклад, як перевірку BR-8 / «без вигаданих записів») або прибрати його.
- **Слабка умова в наявному коді:** `server/test/factories.test.ts:46` перевіряє хелпер через `.resolves.toBeDefined()`. Правило §5 для нових тестів це забороняє; виправлення — окремою задачею.
