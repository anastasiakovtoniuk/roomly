## Як перевірити перший робочий сценарій

**Потрібно:** Node.js 22 LTS (версія в [.nvmrc](.nvmrc)) і npm. Docker і окрема база не потрібні: база — файл SQLite.

```bash
git clone --branch feature/booking-flow https://github.com/anastasiakovtoniuk/roomly.git
cd roomly
npm install
npm run dev
```

Поки сценарій інтегрується, перевіряйте `feature/booking-flow`. Після фінального мерджу в `main` для здачі повторіть перевірку в **новому клоні** командою `git clone https://github.com/anastasiakovtoniuk/roomly.git`, без `--branch`.

`npm run dev` сам:

1. створює `.env` з [.env.example](.env.example), якщо його ще немає (наявний `.env` не змінюється);
2. застосовує наявні міграції бази (`server/prisma/dev.db`);
3. створює адміністратора з `ADMIN_EMAIL` / `ADMIN_PASSWORD` у `.env` (повторний запуск нічого не дублює);
4. запускає сервер і клієнт разом.

| Що | Адреса |
| --- | --- |
| Застосунок (UI) | http://localhost:5173 |
| Перевірка здоров'я через клієнт | http://localhost:5173/api/health |
| API напряму | http://localhost:3000/api/health |

Очікувана відповідь `GET /api/health`:

```json
{ "status": "ok", "database": "ok", "serverTime": "2026-11-03T12:00:00.000Z" }
```

Зупинка — `Ctrl+C` у терміналі. Порти змінюються в `.env` (`SERVER_PORT`, `CLIENT_PORT`).

Дочекайтеся запуску клієнта й сервера. У **другому терміналі**, також у корені `roomly`, створіть демо-дані:

```bash
npm run db:seed:demo -w server
```

Скрипт додає 4 кімнати й майбутні годинні слоти на сьогодні та 3 наступні календарні дні в `APP_TIMEZONE` (типово `Europe/Kyiv`). Студента й бронювання він не створює. Повторний запуск не видаляє дані й не дублює наявні слоти; з `npm run dev` цей seed автоматично не виконується.

### Кроки в браузері — після інтеграції #11–#13

1. Відкрийте [http://localhost:5173](http://localhost:5173) і перейдіть до реєстрації. Використайте нову адресу пошти, ім'я та пароль від 8 символів (не більше 72 байтів UTF-8). Після успіху очікується автоматичний вхід і список кімнат. Якщо видно заглушку сторінки, перевірку зупиніть: UI ще не інтегровано.
2. Оберіть кімнату, наприклад `R101`, і **завтрашню дату за Києвом**. За іншого `APP_TIMEZONE` орієнтуйтеся на дату університету. Перевірте місткість, обладнання, корпус, поверх і вільні слоти. На сьогодні ввечері вільних демо-слотів може вже не бути.
3. Натисніть «Забронювати» біля вільного майбутнього слота. У деталях очікуються кімната, дата, час, статус «активне» та `deadline` із відповіді сервера. Слот має зникнути зі списку вільних.
4. Відкрийте «Мої бронювання» → «Майбутні»: створений запис має бути у списку. Запам'ятайте URL деталей (`/bookings/:id`), час і дедлайн.
5. **До скасування перевірте перезапуск**, як описано нижче: так перевіряється збереження саме активного бронювання.
6. Відкрийте деталі, натисніть «Скасувати» й підтвердьте дію. Очікується статус «скасоване студентом» (`cancelled_by_student`), запис у «Минулих» і знову вільний слот для тієї самої кімнати й дати.
7. Повторіть перезапуск після скасування: запис має лишитися в історії з тим самим статусом. Вийдіть і ввійдіть з тією самою поштою та паролем, щоб також перевірити доступ до збереженого акаунта.

«Майбутні» містять живі бронювання, початок яких ще не настав. Від моменту початку бронювання переходить до «Минулих», але його статус сам собою не змінюється. Будь-яке власне `active` бронювання можна скасувати.

### Збереження після перезапуску

1. У першому терміналі зупиніть `npm run dev` через `Ctrl+C`.
2. У тому самому клоні знову виконайте `npm run dev`. Не видаляйте `server/prisma/dev.db`, не змінюйте `DATABASE_URL` і не скидайте базу; повторний demo-seed для цієї перевірки не потрібний.
3. Оновіть сторінку. Якщо потрібен вхід, використайте той самий акаунт. Перевірте той самий запис: ID, кімнату, час, `deadline` і статус. До скасування він має бути `active`, після — `cancelled_by_student`.

### CI і ШІ-рев'ю

На Pull Request у будь-яку гілку працюють два workflow GitHub Actions:

| Workflow | Коли | Що робить |
| --- | --- | --- |
| [ci.yml](.github/workflows/ci.yml) | Кожен PR, зокрема з форків; push у `main` | `npm ci`, lint, format:check, typecheck, test, збірка клієнта |
| [ai-review.yml](.github/workflows/ai-review.yml) | PR із гілок цього репозиторію; PR із форків пропускаються | Claude Code (`anthropics/claude-code-action@v1`) переглядає diff PR за [спільними правилами аудиту](prompts/5.3_ai_code_review.md) і залишає один коментар |

Правила аудиту агент бере з **базової гілки** PR, а не з гілки самого PR. Тому зміна правил у PR почне діяти лише після мерджу, і PR не може послабити власне рев'ю.

**Секрет.** ШІ-рев'ю працює від підписки Claude робочого акаунта команди, а не від ключа API. Налаштування:

1. Людина з доступом до робочого акаунта входить у Claude Code під ним і виконує `claude setup-token`.
2. Власниця репозиторію додає отриманий токен у Settings → Secrets and variables → Actions → New repository secret з назвою `CLAUDE_CODE_OAUTH_TOKEN`.

Токен не комітити й не вставляти в issue, коментарі, PR чи чат.

**Повторне рев'ю.** Рев'ю запускається автоматично на кожен новий push у гілку PR. Запустити його без змін можна, закривши й знову відкривши PR, або кнопкою Re-run jobs на сторінці запуску workflow AI review.

**Обмеження.**

- PR із форків не перевіряються: їм не доступні секрети репозиторію.
- Без секрету `CLAUDE_CODE_OAUTH_TOKEN` рев'ю пропускається з попередженням у лозі, а workflow не падає.
- Кожен PR і кожен push витрачають ліміти підписки робочого акаунта. Новий push скасовує незавершене рев'ю попереднього коміту того ж PR. Коли ліміти вичерпано, рев'ю падає до їх оновлення.
- Агент лише читає файли й коментує PR: він не змінює код, не схвалює і не зливає PR.

### Основа клієнта (#10)

Клієнт має маршрути `/login`, `/register`, `/rooms`, `/bookings`, `/bookings/:id`. Після відкриття він перевіряє сесію через `/api/auth/me`; гість на захищеному маршруті переходить на `/login`. `/rooms` уже має каталог (#12), `/login` і `/register` — форми входу й реєстрації (#11); `/bookings` і `/bookings/:id` показують власні бронювання, деталі з дедлайном і скасування (#13).

Для підключення екранів використовуйте `useAuth` з `client/src/auth/AuthContext.tsx`: `status`, `user`, `error`, `refresh()`, `login(body)`, `register(body)`, `logout()`. Вхід і реєстрація повертають користувача та оновлюють контекст; після успіху форма переходить на `/rooms`. Усі запити йдуть через функції `client/src/api/auth.ts`, `rooms.ts`, `bookings.ts`; тексти помилок — через `ErrorMessage` або `getErrorMessage`, а не через серверний `message`. Компоненти `Loader`, `EmptyState` і `Layout` спільні для екранів.

Перевірки чистих функцій клієнтського API, дати/часу й помилок полів форм тимчасово лежать у `server/test/clientApi.test.ts`, `clientDateTime.test.ts` та `clientAuthForm.test.ts` і виконуються на наявному Vitest через `npm test`. Це допоміжні перевірки, а не DOM-тести чи повне проходження AC через UI; після появи тестового налаштування клієнта їх можна перенести в `client/`.

### Вхід, реєстрація й вихід (#11)

`/register` створює акаунт студента (імʼя, пошта, пароль від 8 символів) і одразу входить; `/login` — вхід; після успіху обидві форми ведуть на `/rooms`. «Вийти» у шапці видаляє серверну сесію й веде на `/login`. Після перезавантаження сторінки сесія відновлюється через `/api/auth/me`.

Форми перевіряють дані тими самими схемами `RegisterBody`/`LoginBody` із `shared/`, що й сервер (серверна перевірка лишається обов'язковою). Помилки показуються біля полів, зокрема з `details.fields` відповіді `VALIDATION_ERROR`; `EMAIL_ALREADY_REGISTERED` — біля пошти, `INVALID_CREDENTIALS` — загальним повідомленням. Фокус переходить на першу помилку; під час запиту кнопка заблокована, поля лише для читання, повторна відправка не надсилає другий запит. Логіку форм зібрано в `client/src/auth/useAuthForm.ts` і `fieldErrors.ts`, поле з підписом і помилкою — `components/TextField.tsx`.

### Каталог і створення бронювання (#12)

На `/rooms` авторизований користувач бачить реальні кімнати, місткість, розташування й обладнання; обирає кімнату та дату. Студент може забронювати вільний слот одним натисканням; після успіху відкривається `/bookings/:id` (екран деталей додається в #13). Адміністратору кнопки бронювання не показуються; сервер також перевіряє роль.

При конфлікті «Слот щойно зайняли» список слотів оновлюється. Якщо відповідь на запис втрачена, повторний POST автоматично не відправляється: потрібно перевірити «Мої бронювання». Під час запису вибір кімнати й дати заблоковано; за швидкого перемикання попередні читання скасовуються.

Дата й час використовують існуючий `APP_TIMEZONE` (типово `Europe/Kyiv`); Vite передає в браузер лише цей публічний параметр. Після зміни часового поясу перезапустіть Vite, а для production виконайте нову збірку. Інші змінні `.env` у клієнт не передаються. Для перевірки потрібні демо-дані (`npm run db:seed:demo -w server`) й студентський акаунт, створений на `/register`.

**Обмеження MVP щодо «сьогодні».** Початкова дата та мінімальна дата поля беруться з годинника пристрою в часовому поясі університету. Обрана дата задається при відкритті екрана й автоматично не перемикається опівночі, тоді як мінімальна дата оновлюється під час наступного відображення. Якщо екран залишався відкритим через північ, оновіть сторінку або оберіть актуальну дату вручну; якщо годинник пристрою неточний, спочатку синхронізуйте його. Перед демо звірте дату й час пристрою. Допустимість бронювання та зміни його стану перевіряє сервер за власним часом, тому клієнтська дата не дозволяє обійти часові правила.

## Проблема

**Study rooms (навчальні кімнати)** — це невеликі окремі приміщення в університетських бібліотеках або на території кампусу, які студенти можуть забронювати на конкретний часовий слот.

У межах проєкту **Roomly** йдеться насамперед про кімнати для групового використання:

* роботи над командними проєктами;
* спільної підготовки до іспитів;
* проведення навчальних зустрічей;
* обговорень і командної роботи.

Такий формат поширений у багатьох університетах Європи та Північної Америки.

Проблема полягає в тому, що плани студентської групи можуть змінитися: учасники не встигають прийти, переносять зустріч або знаходять інше місце. При цьому бронювання часто не скасовують, тому кімната продовжує відображатися як зайнята, хоча фактично не використовується.

Через це інша група, якій приміщення потрібне в цей час, не може його забронювати. У результаті обмежений простір університету використовується неефективно, а адміністрація не має зручного способу перевірити, чи справді заброньована кімната використовується.

## Цільова аудиторія

Основними користувачами застосунку є:

* студенти, які працюють над груповими проєктами;
* студентські команди, яким потрібне приміщення для зустрічей, обговорень або підготовки до занять;
* працівники університетських бібліотек і кампусів;
* адміністратори, відповідальні за навчальні кімнати, розклад і контроль бронювань.

## Початкова ідея рішення

**Roomly** — це мобільний застосунок для пошуку та бронювання навчальних кімнат в університетських бібліотеках або на території кампусу.

### Основні можливості

Користувач зможе:

* переглядати доступні навчальні кімнати;
* перевіряти їхню місткість, розташування та доступне обладнання;
* обирати дату й вільний часовий слот;
* створювати та скасовувати бронювання;
* переглядати історію своїх бронювань;
* отримувати нагадування про майбутнє бронювання.

### Підтвердження присутності

Через **10–15 хвилин** після початку заброньованого часу студент повинен підтвердити свою присутність, відсканувавши камерою смартфона QR-код, розміщений у кімнаті.

Якщо користувач не підтвердить присутність у визначений час, бронювання автоматично скасується, а кімната знову стане доступною для інших студентів.

### Ролі в застосунку

У застосунку передбачено дві основні ролі:

* **Користувач** — переглядає кімнати й часові слоти, створює та скасовує бронювання, підтверджує присутність за допомогою QR-коду.
* **Адміністратор** — додає та редагує кімнати й часові слоти, створює QR-коди, переглядає всі бронювання, керує обліковими записами студентів і контролює використання приміщень.

## Очікуваний результат

Застосунок допоможе:

* ефективніше використовувати навчальні кімнати;
* зменшити кількість невикористаних бронювань;
* зробити процес бронювання зручним і прозорим;
* спростити організацію групової роботи студентів.
