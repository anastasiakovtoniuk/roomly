## Як перевірити застосунок

**Потрібно:** Node.js 22 LTS (версія в [.nvmrc](.nvmrc)) і npm. Docker і окрема база не потрібні: база — файл SQLite.

```bash
git clone https://github.com/anastasiakovtoniuk/roomly.git
cd roomly
npm install
npm run dev
```

Клон без `--branch` бере `main`. Поки другий сценарій не злитий у `main` (фінальний PR, issue #56), перевіряйте інтеграційну гілку: `git clone --branch feature/checkin-admin …`.

`npm run dev` сам:

1. створює `.env` з [.env.example](.env.example), якщо його ще немає (наявний `.env` не змінюється);
2. застосовує наявні міграції бази (`server/prisma/dev.db`);
3. створює адміністратора з `ADMIN_EMAIL` / `ADMIN_PASSWORD` у `.env` (повторний запуск нічого не дублює);
4. запускає сервер і клієнт разом.

| Що | Адреса |
| --- | --- |
| Застосунок (UI) | http://localhost:5173 |
| Перевірка здоров'я через клієнт | http://localhost:5173/api/health |
| API напряму | http://localhost:3000/api/health |

Очікувана відповідь `GET /api/health`:

```json
{ "status": "ok", "database": "ok", "serverTime": "2026-11-03T12:00:00.000Z" }
```

Зупинка — `Ctrl+C` у терміналі. Порти змінюються в `.env` (`SERVER_PORT`, `CLIENT_PORT`).

Дочекайтеся запуску клієнта й сервера. У **другому терміналі**, також у корені `roomly`, створіть демо-дані:

```bash
npm run db:seed:demo -w server
```

Скрипт додає 4 кімнати й майбутні годинні слоти на сьогодні та 3 наступні календарні дні в `APP_TIMEZONE` (типово `Europe/Kyiv`). Студента й бронювання він не створює. Повторний запуск не видаляє дані й не дублює наявні слоти; з `npm run dev` цей seed автоматично не виконується.

### Перший сценарій: бронювання слота студентом

1. Відкрийте [http://localhost:5173](http://localhost:5173) і перейдіть до реєстрації. Використайте нову адресу пошти, ім'я та пароль від 8 символів (не більше 72 байтів UTF-8). Після успіху очікується автоматичний вхід і список кімнат.
2. Оберіть кімнату, наприклад `R101`, і **завтрашню дату за Києвом**. За іншого `APP_TIMEZONE` орієнтуйтеся на дату університету. Перевірте місткість, обладнання, корпус, поверх і вільні слоти. На сьогодні ввечері вільних демо-слотів може вже не бути.
3. Натисніть «Забронювати» біля вільного майбутнього слота. У деталях очікуються кімната, дата, час, статус «активне» та `deadline` із відповіді сервера. Слот має зникнути зі списку вільних.
4. Відкрийте «Мої бронювання» → «Майбутні»: створений запис має бути у списку; якщо до початку менше доби, над ним є нагадування в застосунку. Запам'ятайте URL деталей (`/bookings/:id`), час і дедлайн.
5. **До скасування перевірте перезапуск**, як описано нижче: так перевіряється збереження саме активного бронювання.
6. Відкрийте деталі, натисніть «Скасувати бронювання» й підтвердьте дію. Очікується статус «скасоване студентом» (`cancelled_by_student`), запис у «Минулих» і знову вільний слот для тієї самої кімнати й дати.
7. Повторіть перезапуск після скасування: запис має лишитися в історії з тим самим статусом. Вийдіть і ввійдіть з тією самою поштою та паролем, щоб також перевірити доступ до збереженого акаунта.

«Мої бронювання» мають три вкладки: «Майбутні» — слот ще не почався; «Активні» — `active` або `confirmed`, слот почався й не завершився; «Минулі» — решта ([рішення 5](docs/scenarios/checkin_admin_flow.md)). Будь-яке власне `active` бронювання можна скасувати.

### Збереження після перезапуску

1. У першому терміналі зупиніть `npm run dev` через `Ctrl+C`.
2. У тому самому клоні знову виконайте `npm run dev`. Не видаляйте `server/prisma/dev.db`, не змінюйте `DATABASE_URL` і не скидайте базу; повторний demo-seed для цієї перевірки не потрібний.
3. Оновіть сторінку. Якщо потрібен вхід, використайте той самий акаунт. Перевірте той самий запис: ID, кімнату, час, `deadline` і статус. До скасування він має бути `active`, після — `cancelled_by_student`.

### Другий сценарій: підтвердження присутності й автоскасування

Межі й рішення — у [checkin_admin_flow.md](docs/scenarios/checkin_admin_flow.md). Демо-seed створює слоти лише на майбутнє, тому для check-in потрібен слот, що починається за кілька хвилин. Grace period — 15 хв (гіпотеза H01).

1. **Адміністратор.** Увійдіть з `ADMIN_EMAIL` / `ADMIN_PASSWORD` з `.env`. «Адмін: кімнати» → у картці кімнати створіть слот, що починається за 2–3 хв і закінчується щонайменше через 20 хв. Там само відкрийте «QR-код для друку» → «Друкувати» (можна «Зберегти як PDF»): на сторінці лише QR і назва кімнати.
2. **Студент** (інший браузер або приватне вікно) бронює цей слот до початку.
3. Після початку слота: «Мої бронювання» → «Активні» або деталі бронювання — «Підтвердіть присутність до HH:MM» і відлік до дедлайну.
4. «Підтвердити присутність» → покажіть QR вебкамері (на десктопі достатньо `localhost`; телефон — лише через HTTPS, див. нижче). Очікується «Присутність підтверджено» і статус «Підтверджене». Підтвердити може будь-який студент, а не лише власник.
5. **Без скану:** створіть друге бронювання й не підтверджуйте його. Через 15 хв після початку сервер переведе його в «Автоскасоване» (фонова перевірка кожні 30 с), навіть якщо застосунок закритий; запис з'явиться в «Минулих».
6. **Адміністратор:** «Адмін: бронювання» — бронювання всіх студентів зі статусами й позначкою «за QR» / «вручну»; «Підтвердити вручну» доступне для активного бронювання у вікні підтвердження.

Не підключено й не перевіряється: адміністративне скасування (US-A.6, Q03/Q18), редагування й видалення слотів (Q17/G6), push-сповіщення. Ручний чекліст із результатами — [testing-report.md](docs/testing-report.md) §2.

### Автоматичні перевірки

Одна команда запускає всі автотести:

```bash
npm test
```

Вона виконує `vitest run` у `server/` (інтеграційні тести API через Supertest на окремій SQLite-базі `server/prisma/test.db`, створеній міграціями; робоча `dev.db` не змінюється) і в `client/` (чиста логіка й компоненти в jsdom). Таймер автоскасування в тестах не стартує, час підміняється. Повна перевірка перед PR, з кореня репозиторію:

```bash
npm run lint
npm run format:check
npm run typecheck
npm test
npm run build
```

Що автоматизуємо, а що перевіряємо вручну, — [тестова стратегія](docs/testing-strategy.md); що покрито, ручний чекліст, знайдені баги й результати прогону — [звіт про тестування](docs/testing-report.md).

### Перевірка на телефоні через HTTPS

Камера телефона працює лише в захищеному контексті: `https://` або `localhost`. Адреса ноутбука в мережі по HTTP (`http://192.168.…:5173`) не підходить: вхід і бронювання відкриються, але екран підтвердження присутності не отримає доступ до камери. Для перевірки на телефоні використовуйте HTTPS-тунель `ngrok`.

**Одноразове налаштування.**

1. Встановіть [ngrok](https://ngrok.com/download) і зареєструйтеся (безкоштовного акаунта достатньо).
2. Виконайте `ngrok config add-authtoken <ваш токен>`. Токен зберігається в локальній конфігурації ngrok. Не додавайте його в репозиторій, `.env`, `.env.example`, issue, коментарі, PR чи промпти.
3. У кабінеті ngrok отримайте безкоштовний статичний домен (Domains) і впишіть його у свій `.env`: `TUNNEL_DOMAIN="my-name.ngrok-free.app"` (лише домен, без `https://` і без шляху).

**Запуск.**

```bash
npm run dev:tunnel
```

Команда запускає те саме, що `npm run dev`, і паралельно тунель до клієнта (`CLIENT_PORT`). Відкрийте на телефоні `https://<TUNNEL_DOMAIN>`. Без `TUNNEL_DOMAIN` або без встановленого ngrok команда зупиняється з поясненням до старту серверів. Звичайний `npm run dev` тунель не запускає й від ngrok не залежить. Vite дозволяє звернення лише з домену, заданого в `TUNNEL_DOMAIN`; інші чужі хости він відхиляє.

**Обмеження.**

- **Безпека.** Тунель відкриває весь застосунок з інтернету, зокрема вхід адміністратора. `npm run dev:tunnel` попереджає, якщо `ADMIN_PASSWORD` у `.env` лишився паролем із `.env.example` (він публічний). Змініть його перед запуском тунелю. Seed не оновлює пароль уже створеного адміністратора, тож після зміни `.env` видаліть користувача `admin` у `npm run db:studio -w server` і перезапустіть, щоб seed створив його з новим паролем.
- Безкоштовний ngrok при першому відкритті показує сторінку-попередження: натисніть, щоб продовжити.
- Увесь трафік з телефона проходить через сервери ngrok: використовуйте лише тестові дані, не реальні дані студентів.
- Скрипт очікує офіційний виконуваний файл `ngrok` у PATH (на Windows це `ngrok.exe`); обгортку `.cmd`, встановлену, наприклад, через npm, він не розпізнає й повідомить, що ngrok не знайдено.
- Тунель працює, поки відкритий термінал із `npm run dev:tunnel`; `Ctrl+C` зупиняє сервери, клієнт і тунель разом.
- Cookie сесії сервер виставляє без `Secure` (він бачить внутрішній HTTP від Vite), але з HTTPS-сторінки браузер її приймає: вхід працює через той самий домен.

### CI і ШІ-рев'ю

На Pull Request у будь-яку гілку працюють два workflow GitHub Actions:

| Workflow | Коли | Що робить |
| --- | --- | --- |
| [ci.yml](.github/workflows/ci.yml) | Кожен PR у будь-яку гілку (зокрема в `feature/checkin-admin`), зокрема з форків; push у `main` | `npm ci`, lint, format:check, typecheck, `npm test` (серверні й клієнтські тести), збірка клієнта |
| [ai-review.yml](.github/workflows/ai-review.yml) | PR із гілок цього репозиторію; PR із форків пропускаються | Claude Code (`anthropics/claude-code-action@v1`) переглядає diff PR за [спільними правилами аудиту](prompts/5.3_ai_code_review.md) і залишає один коментар; якщо агент завершився без коментаря, останній крок «Verify review comment was posted» робить job червоним |

Правила аудиту агент бере з **базової гілки** PR, а не з гілки самого PR. Тому зміна правил у PR почне діяти лише після мерджу, і PR не може послабити власне рев'ю. Для PR у `feature/checkin-admin` діють правила з цієї гілки; для фінального PR у `main` — правила з `main`, тож зміни в «Спільних правилах аудиту» мають потрапити в `main` до відкриття фінального PR (issue #56).

Правила охоплюють і ризики другого сценарію: умовні переходи статусів (підтвердження й автоскасування), `qrToken` лише в адмін-ендпоінті, guard `/api/admin/*`, якість тестів (ID критерію, без моків БД і слабких тверджень, без фіксації відкритих питань) та межі MVP.

**Секрет.** ШІ-рев'ю працює від підписки Claude робочого акаунта команди, а не від ключа API. Налаштування:

1. Людина з доступом до робочого акаунта входить у Claude Code під ним і виконує `claude setup-token`.
2. Власниця репозиторію додає отриманий токен у Settings → Secrets and variables → Actions → New repository secret з назвою `CLAUDE_CODE_OAUTH_TOKEN`.

Токен не комітити й не вставляти в issue, коментарі, PR чи чат.

**Повторне рев'ю.** Рев'ю запускається автоматично на кожен новий push у гілку PR. Запустити його без змін можна, закривши й знову відкривши PR, або кнопкою Re-run jobs на сторінці запуску workflow AI review.

**Обмеження.**

- PR із форків не перевіряються: їм не доступні секрети репозиторію.
- Без секрету `CLAUDE_CODE_OAUTH_TOKEN` рев'ю пропускається з попередженням у лозі, а workflow не падає.
- Кожен PR і кожен push витрачають ліміти підписки робочого акаунта. Новий push скасовує незавершене рев'ю попереднього коміту того ж PR. Коли ліміти вичерпано, рев'ю падає до їх оновлення.
- Агент лише читає файли й коментує PR: він не змінює код, не схвалює і не зливає PR.
- Зелена перевірка `review` означає, що коментар опубліковано (це перевіряє окремий крок). Якщо вона червона з повідомленням про відсутність коментаря, перезапустіть job кнопкою Re-run jobs.

### Основа клієнта (#10)

Клієнт має маршрути `/login`, `/register`, `/rooms`, `/bookings`, `/bookings/:id`, а з другого сценарію — `/check-in` і `/admin/rooms`, `/admin/rooms/:roomId/qr`, `/admin/bookings`. Після відкриття він перевіряє сесію через `/api/auth/me`; гість на захищеному маршруті переходить на `/login`. `/rooms` уже має каталог (#12), `/login` і `/register` — форми входу й реєстрації (#11); `/bookings` і `/bookings/:id` показують власні бронювання, деталі з дедлайном і скасування (#13).

Для підключення екранів використовуйте `useAuth` з `client/src/auth/AuthContext.tsx`: `status`, `user`, `error`, `refresh()`, `login(body)`, `register(body)`, `logout()`. Вхід і реєстрація повертають користувача та оновлюють контекст; після успіху форма переходить на `/rooms`. Усі запити йдуть через функції `client/src/api/auth.ts`, `rooms.ts`, `bookings.ts`; тексти помилок — через `ErrorMessage` або `getErrorMessage`, а не через серверний `message`. Компоненти `Loader`, `EmptyState` і `Layout` спільні для екранів.

Тести клієнта лежать поряд із модулями: `client/src/api/api.test.ts`, `client/src/lib/dateTime.test.ts`, `client/src/lib/bookingView.test.ts`, `client/src/auth/fieldErrors.test.ts` (чиста логіка, середовище `node`) і `client/src/components/EmptyState.test.tsx` (приклад компонентного тесту в `jsdom`). Вони виконуються Vitest із `client/` і входять у кореневий `npm test` разом із серверними. Це допоміжні перевірки, а не повне проходження AC через UI. Спільні хелпери серверних тестів (кімнати, слоти, користувачі, сесії студента й адміністратора) лежать у `server/test/helpers/`; тестова база спільна й не очищується, кожен тест створює власні унікальні дані, а файли тестів виконуються по черзі.

### Вхід, реєстрація й вихід (#11)

`/register` створює акаунт студента (імʼя, пошта, пароль від 8 символів) і одразу входить; `/login` — вхід; після успіху обидві форми ведуть на `/rooms`. «Вийти» у шапці видаляє серверну сесію й веде на `/login`. Після перезавантаження сторінки сесія відновлюється через `/api/auth/me`.

Форми перевіряють дані тими самими схемами `RegisterBody`/`LoginBody` із `shared/`, що й сервер (серверна перевірка лишається обов'язковою). Помилки показуються біля полів, зокрема з `details.fields` відповіді `VALIDATION_ERROR`; `EMAIL_ALREADY_REGISTERED` — біля пошти, `INVALID_CREDENTIALS` — загальним повідомленням. Фокус переходить на першу помилку; під час запиту кнопка заблокована, поля лише для читання, повторна відправка не надсилає другий запит. Логіку форм зібрано в `client/src/auth/useAuthForm.ts` і `fieldErrors.ts`, поле з підписом і помилкою — `components/TextField.tsx`.

### Каталог і створення бронювання (#12)

На `/rooms` авторизований користувач бачить реальні кімнати, місткість, розташування й обладнання; обирає кімнату та дату. Студент може забронювати вільний слот одним натисканням; після успіху відкривається `/bookings/:id` (#13). Адміністратору кнопки бронювання не показуються; сервер також перевіряє роль.

При конфлікті «Слот щойно зайняли» список слотів оновлюється. Якщо відповідь на запис втрачена, повторний POST автоматично не відправляється: потрібно перевірити «Мої бронювання». Під час запису вибір кімнати й дати заблоковано; за швидкого перемикання попередні читання скасовуються.

Дата й час використовують існуючий `APP_TIMEZONE` (типово `Europe/Kyiv`); Vite передає в браузер лише цей публічний параметр. Після зміни часового поясу перезапустіть Vite, а для production виконайте нову збірку. Інші змінні `.env` у клієнт не передаються. Для перевірки потрібні демо-дані (`npm run db:seed:demo -w server`) й студентський акаунт, створений на `/register`.

**Обмеження MVP щодо «сьогодні».** Початкова дата та мінімальна дата поля беруться з годинника пристрою в часовому поясі університету. Обрана дата задається при відкритті екрана й автоматично не перемикається опівночі, тоді як мінімальна дата оновлюється під час наступного відображення. Якщо екран залишався відкритим через північ, оновіть сторінку або оберіть актуальну дату вручну; якщо годинник пристрою неточний, спочатку синхронізуйте його. Перед демо звірте дату й час пристрою. Допустимість бронювання та зміни його стану перевіряє сервер за власним часом, тому клієнтська дата не дозволяє обійти часові правила.

### Підтвердження присутності за QR — сервер (#40)

`POST /api/check-ins` з тілом `{ "qrToken": "…" }` підтверджує поточне бронювання кімнати, якій належить QR. Підтвердити може будь-який авторизований студент, не лише власник; власник не змінюється, у відповіді — лише роль того, хто підтвердив. Успіх — `confirmed` або, для повтору, `already_confirmed` без змін; помилки — `QR_UNKNOWN`, `NO_CURRENT_BOOKING`, `CHECK_IN_WINDOW_CLOSED`, `CHECK_IN_TOO_EARLY` (`docs/contracts/api_spec.md` §8). Раннього вікна немає, рівно в дедлайн вікно ще відкрите (Q01, рішення 4 у `docs/scenarios/checkin_admin_flow.md`). Екран — `/check-in` (#43): сканування камерою або ручне введення коду, повтор після мережевої помилки лише за кнопкою.

### Адміністрування кімнат, слотів і QR — сервер (#41)

Модуль `server/src/modules/admin/` закриває весь `/api/admin/*` перевіркою ролі із сесії: гість отримує `UNAUTHENTICATED`, студент — `FORBIDDEN`, зокрема на неіснуючому шляху. Ендпоінти (`docs/contracts/api_spec.md` §9):

- `POST /api/admin/rooms` — створити кімнату (`201 { room }`); `qrToken` генерує сервер, у відповіді його немає;
- `PATCH /api/admin/rooms/:roomId` — змінити лише надіслані поля, `equipment` замінюється цілком; `qrToken` не змінюється;
- `POST /api/admin/rooms/:roomId/slots` — створити слот (`201 { slot }`): кінець пізніше за початок і пізніше за поточний момент, обидва в одну дату університету, без перетину з іншими слотами кімнати (`SLOT_OVERLAP`); суміжні слоти дозволені. Ці правила — **[Пропозиція]** G7/Q10. Вставка й перевірка перетину виконуються в одній транзакції;
- `GET /api/admin/rooms/:roomId/qr` — `{ roomId, roomName, qrToken }`; єдине місце, де віддається токен, повтор дає той самий.

Редагування й видалення слотів немає (Q17/G6). Назва кімнати не унікальна (Q09). Екрани: `/admin/rooms` — кімнати й слоти (#45), `/admin/rooms/:roomId/qr` — QR і друк (#46).

### Усі бронювання й ручне підтвердження — сервер (#42)

- `GET /api/admin/bookings` — усі бронювання всіх студентів за спаданням початку слота, кожне з власником `student: { id, name, email }`, і `serverTime`. Перед читанням виконується ліниве автоскасування, тож прострочене `active` уже показано як `auto_cancelled`.
- `POST /api/admin/bookings/:bookingId/confirm` — ручне підтвердження з тим самим вікном і тим самим умовним оновленням, що й `POST /api/check-ins`. Відповідь — `CheckInResult` з `confirmedBy: "admin"`; повтор — `already_confirmed` (**[Пропозиція]** Q06). Помилки: `BOOKING_NOT_FOUND`, `BOOKING_STATUS_CONFLICT` (скасоване студентом, `details.currentStatus`), `CHECK_IN_WINDOW_CLOSED` (після дедлайну або автоскасоване), `CHECK_IN_TOO_EARLY` (до початку). Рівно в дедлайн підтвердження ще можливе.

Екран — `/admin/bookings` (#46). Адміністративне скасування (US-A.6) не реалізоване: його статус залежить від G2/Q03, Q18.

### Автоскасування, відлік і нагадування (#39, #44)

Сервер переводить `active` після `deadline` в `auto_cancelled`: фонова перевірка кожні 30 с (`server/src/modules/bookings/autoCancelScheduler.ts`, стартує лише з `server/src/index.ts`) і ліниве скасування перед читанням, створенням і підтвердженням; підтверджені й скасовані записи не переписуються. Клієнт показує відлік і повідомлення «Підтвердіть присутність до HH:MM» за `serverTime` і `deadline` з відповіді сервера, а нагадування — у «Майбутніх», коли до початку ≤ 24 год (гіпотеза H02, Q05/G10 відкрите). Push немає.

## Проблема

**Study rooms (навчальні кімнати)** — це невеликі окремі приміщення в університетських бібліотеках або на території кампусу, які студенти можуть забронювати на конкретний часовий слот.

У межах проєкту **Roomly** йдеться насамперед про кімнати для групового використання:

* роботи над командними проєктами;
* спільної підготовки до іспитів;
* проведення навчальних зустрічей;
* обговорень і командної роботи.

Такий формат поширений у багатьох університетах Європи та Північної Америки.

Проблема полягає в тому, що плани студентської групи можуть змінитися: учасники не встигають прийти, переносять зустріч або знаходять інше місце. При цьому бронювання часто не скасовують, тому кімната продовжує відображатися як зайнята, хоча фактично не використовується.

Через це інша група, якій приміщення потрібне в цей час, не може його забронювати. У результаті обмежений простір університету використовується неефективно, а адміністрація не має зручного способу перевірити, чи справді заброньована кімната використовується.

## Цільова аудиторія

Основними користувачами застосунку є:

* студенти, які працюють над груповими проєктами;
* студентські команди, яким потрібне приміщення для зустрічей, обговорень або підготовки до занять;
* працівники університетських бібліотек і кампусів;
* адміністратори, відповідальні за навчальні кімнати, розклад і контроль бронювань.

## Початкова ідея рішення

**Roomly** — це мобільний застосунок для пошуку та бронювання навчальних кімнат в університетських бібліотеках або на території кампусу.

### Основні можливості

Користувач зможе:

* переглядати доступні навчальні кімнати;
* перевіряти їхню місткість, розташування та доступне обладнання;
* обирати дату й вільний часовий слот;
* створювати та скасовувати бронювання;
* переглядати історію своїх бронювань;
* отримувати нагадування про майбутнє бронювання.

### Підтвердження присутності

Через **10–15 хвилин** після початку заброньованого часу студент повинен підтвердити свою присутність, відсканувавши камерою смартфона QR-код, розміщений у кімнаті.

Якщо користувач не підтвердить присутність у визначений час, бронювання автоматично скасується, а кімната знову стане доступною для інших студентів.

### Ролі в застосунку

У застосунку передбачено дві основні ролі:

* **Користувач** — переглядає кімнати й часові слоти, створює та скасовує бронювання, підтверджує присутність за допомогою QR-коду.
* **Адміністратор** — додає та редагує кімнати й часові слоти, створює QR-коди, переглядає всі бронювання, керує обліковими записами студентів і контролює використання приміщень.

## Очікуваний результат

Застосунок допоможе:

* ефективніше використовувати навчальні кімнати;
* зменшити кількість невикористаних бронювань;
* зробити процес бронювання зручним і прозорим;
* спростити організацію групової роботи студентів.
