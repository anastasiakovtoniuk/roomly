## Зінченко Вероніка

### Issue #10: основа клієнта

**Інженерне завдання асистенту:** перевірити `lint`, `typecheck`, тести й збірку; виправляти причину помилок, зберігаючи strict і правила ESLint.

- PowerShell блокує `npm.ps1`: команди запущено через `npm.cmd`, політику виконання не змінено.
- `npm ci` зупинився через заборону запису в кеш Prisma за межами репозиторію; повторне встановлення за lock-файлом із дозволеним доступом завершилося успішно. Версії залежностей не змінювалися.
- ESLint `react-hooks/set-state-in-effect` позначив виклик асинхронного відновлення сесії з `try/catch` в ефекті. Відновлення переписано на обробники результату Promise: стан змінюється лише після відповіді сервера. Правило не вимикалося.
- Підготовка тестів Prisma локально падала, а відображення помилки маскував [дефект Vitest 5.0.5/Vite 8.3.5](https://github.com/vitest-dev/vitest/issues/11682). Діагностичний запуск з `--fsModuleCache=false` показав помилку `migrate deploy`. Після явного шляху до встановленого `schema-engine-windows.exe` і `RUST_LOG=info` штатний `npm test` пройшов: 126 тестів для окремої зміни #10. Тимчасовий діагностичний вивід `globalSetup` повернуто; версії й конфігурація перевірок не змінені.
- Локальне ШІ-рев'ю знайшло два випадки: обірваний JSON міг лишити сесію в `loading`, а `UNAUTHENTICATED` після виходу в іншій вкладці не оновлював контекст. Виправлено: нечитабельна успішна відповідь дає `NetworkError`, відновлення перехоплює rejection, захищений API із `UNAUTHENTICATED` запускає повторну перевірку `/me`. Додано регресійні тести транспорту.

### Issue #9: демо-дані й підтвердження збереження після перезапуску

`npm run lint`, `typecheck`, `build -w client` пройшли з першого запуску; `npm test` — 115 тестів (108 наявних + 7 нових) після виправлення нижче.

1. **Нестабільний тест через спільну тестову базу.** Окремо `seedDemo.test.ts` проходив, а разом із `persistence.test.ts` падав: `expected 1 to be +0`. Причина: тест порівнював загальні лічильники `user.count()` і `booking.count()` до й після seed, а інший файл тестів паралельно створював бронювання в тій самій `test.db`. Промпт: «Запусти npm run lint, format:check, typecheck, test; виправ помилки». Результат: перевірку звужено до бронювань на слотах демо-кімнат (має бути 0) з коментарем, чому загальні лічильники тут не годяться; твердження про ідемпотентність і слоти не послаблено. Конфігурацію Vitest не змінено.
2. **Форматування.** `npx prettier --write` для `seedDemo.test.ts` (перенесення рядків), логіку не змінено, `format:check` зелений.
3. **CI на PR #24 впав: `seedDemo.test.ts:50`, `expected 3 to be 4`** (локально 115/115). Промпт: «Не вгадуй, а діагностуй: що рахує рядок 50; чи залежить тест від спільної `test.db` і паралельних файлів (`fileParallelism`, `globalSetup`); запусти з `TZ=UTC` і порожнім `APP_TIMEZONE`; відтвори падіння (npm test ×5). Виправ причину, а не послабляй перевірку.» Діагностика:
   - рядок 50 — `result.roomsCreated`: seed створив 3 кімнати з 4, одну вважав наявною;
   - `rooms.test.ts` (тест FB-12) створює кімнату з назвою `R101` — тією самою, що й перша демо-кімната; файли виконуються паралельно (`fileParallelism` не вимкнено), а `globalSetup` створює одну `test.db` на запуск; seed шукає кімнату за назвою, тож, якщо `rooms.test.ts` встигає першим, чужа `R101` рахується «наявною». Доказ: у `test.db` зеленого запуску дві `R101` — демо (36 слотів) і з `rooms.test.ts` (створена на 7 с пізніше, 0 слотів); тимчасовий тест, що спершу створює чужу `R101`, детерміновано дав `expected 3 to be 4`;
   - часовий пояс ні до чого: `vitest.config.ts` жорстко задає `APP_TIMEZONE=Europe/Kyiv`, а з `TZ=UTC` і порожнім `APP_TIMEZONE` це падіння не з'являлося;
   - **друга, окрема причина** знайшлася під час повторних запусків (10 поспіль, 3 з падіннями): `Test timed out in 5000ms` у seed-тесті (6–10 с) і в сусідніх тестах `bookings*`. `seedDemo` робив окремі `findFirst` і `create` на кожен слот (~260 запитів), тримаючи спільну SQLite.

   Виправлення: `seedDemo(rooms = DEMO_ROOMS)` — тест передає ті самі `DEMO_ROOMS` з унікальним префіксом запуску й шукає лише свої кімнати; скрипт, як і раніше, бере `DEMO_ROOMS`. У `seedDemo` наявні слоти кімнати читаються одним запитом, перетин (BR-13) перевіряється в пам'яті, нові слоти створюються одним `createMany`. Твердження тесту не послаблено, таймаут і конфігурацію Vitest не змінено. Результат: найдовший seed-тест 490 мс замість 6–10 с; `npm test` 5 разів поспіль і 5 разів з `TZ=UTC` — 115/115; `lint`, `format:check`, `typecheck` — без помилок; повторний `npm run db:seed:demo -w server` на `dev.db` — «створено 0, пропущено 112».
