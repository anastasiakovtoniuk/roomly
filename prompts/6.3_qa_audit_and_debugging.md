# 6.3 Аудит якості тестів і пошук багів

Промпти для перевірки якості тестів (аудит покриття, пошук пропущених граничних випадків, прийом «зламай код навмисно») і для діагностики знайдених багів. Кожна учасниця заповнює лише свою секцію: issue, промпт, знахідки (мутація → тест, що впав; пропущені випадки; причина й виправлення бага) і результат.

### Issue #50: «зламай код навмисно» для check-in і автоскасування

**Промпт:** «Для кожної мутації тимчасово зіпсуй код, запусти тести, переконайся, що названа група червоніє, поверни код (`git diff` порожній після кожної): (а) прибрати `status: 'active'` у `cancelExpiredBookings`; (б) у check-in прибрати умову `deadline >= now`; (в) дозволити підтвердження для `auto_cancelled`; (г) прибрати `requireRole('student')` з маршруту check-in; (д) повертати в `CheckInResult` дані власника; (е) у `confirmCurrentBooking` прибрати гілку `cancelled_by_student` → `NO_CURRENT_BOOKING`. Якщо тест не впав, він слабкий: посили.»

**Як виконано:** кожна мутація — окремий perl-скрипт, перевірений `diff` на копії до прогону (щоб «жива» мутація не виявилась незастосованою). Прогін `server/test/checkIns.ac.test.ts` + `autoCancel.ac.test.ts`, далі відновлення з резервних копій і звірка `cmp`; після всіх мутацій `git diff -- server/src` порожній.

| Мутація | Червоні тести |
| --- | --- |
| (а) `cancelExpiredBookings` без `status: 'active'` | 5: US-5.1-AC-02; SYS-AC-02 (повторне скасування); SYS-AC-03 ×2 (студент, адміністратор); SYS-AC-05 |
| (б) `confirmableWhere` без `deadline: { gte: at }` | 1: SYS-AC-07, US-5.1-AC-06 — `confirmCurrentBooking` о 10:16 для `active` |
| (в) `confirmableWhere` приймає `auto_cancelled` і в `checkIn` прибрано охорону `auto_cancelled` | 2 (після посилення): SYS-AC-07 «автоскасування виграло — скан у межах вікна» (C25); SYS-AC-07 одночасні check-in і автоскасування (C21) |
| (г) `checkInsRouter` без `requireRole('student')` | 1: US-5.2-AC-01 (api_spec §8) адміністратор → 403 |
| (д) `confirmCurrentBooking` віддає `owner: { id, name, email }` у `booking` | 1: US-5.2-AC-01, US-5.2-AC-04 — даних власника у відповіді немає |

**Слабке місце, знайдене мутацією (в).** У першому прогоні (в) ловив лише C21, тобто тест гонки `Promise.allSettled` без гарантованого порядку. Такий кілер ненадійний: порядок у гонці не зафіксовано. Додано детермінований C25: спершу `cancelExpiredBookings(10:16)`, потім скан із годинником 10:05 → 422 `CHECK_IN_WINDOW_CLOSED`, запис `auto_cancelled`. У трьох прогонах поспіль із мутацією (в) C25 червоний. C21 червоніє теж, бо підтверджений після автоскасування запис зберігає `cancelledAt`, а тест вимагає `cancelledAt = null`.

**Мутації (б) і (г) ловить по одному тесту.** (б) на HTTP-рівні не видно: ліниве автоскасування в `checkIn` скасовує прострочений запис раніше, ніж спрацює умова оновлення; тому її ловить лише прямий виклик `confirmCurrentBooking` (C23). Межа «рівно в дедлайн» свідомо не тестується (рішення 4).

**Знахідки.** На незміненому коді всі 36 тестів зелені; багів у #39/#40 не знайдено, issue `bug` не заводилося.
