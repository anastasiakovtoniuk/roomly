# Планування роботи: тексти GitHub issues

Універсальний промпт: підходить для будь-якого етапу чи сценарію. Конкретика задається у блоці «Вхідні дані».

## Вхідні дані (заповнюється перед запуском)

- **Завдання:** посилання на текст завдання або його вимоги списком, включно з тим, що має лежати в репозиторії в кінці.
- **Обсяг:** що саме реалізуємо (епік, історії, ID) і що явно поза обсягом.
- **Інтеграційна гілка:** назва гілки, в яку зливаються задачі.
- **Виключення:** що не включати в issues.

## Промпт

Ти допомагаєш команді спланувати виконання завдання. Напиши тексти GitHub issues і створи їх у репозиторії. Спершу зроби підготовку, потім дотримуйся вимог.

### Підготовка

1. Прочитай `README.md`: склад команди й ролі учасників.
2. Прочитай `AGENTS.md` і `CLAUDE.md`: стек, структуру, інваріанти, заборони, команди перевірок, правила Git-процесу.
3. Прочитай технічні контракти й вимоги, на які посилається завдання, звір ID історій і критеріїв приймання.
4. Прочитай конфігурацію CI, щоб знати, які перевірки вже є.
5. Визнач відповідність «учасниця з README → GitHub-акаунт»: список колабораторів (`gh api repos/:owner/:repo/collaborators --jq '.[].login'`) і імена їхніх профілів (`gh api users/<login> --jq .name`). Якщо відповідність для когось неоднозначна, запитай, хто є хто, і лише потім створюй issues.
6. Подивись наявні issues, мітки й milestone (`gh issue list --state all`, `gh label list`). Якщо issues для цього завдання вже є, не дублюй їх: звір з вимогами нижче й онови наявні.

### Вимоги до issues

1. **Покриття завдання.** Разом issues закривають усі вимоги з розділу «Вхідні дані», включно з кодом, тестами, промптами, перевірками якості, CI, ШІ-рев'ю, мерджем, документацією й здачею. Те, що є у виключеннях, не включай.
2. **Розподіл за ролями.** Кожна учасниця отримує issues за своєю роллю й приблизно рівний обсяг. Усі пишуть код і ведуть власні промпти; жодну частину не перекладай на одну людину. Спільні й процесні задачі розподіли між усіма. Виконавицю призначай через поле Assignees (`gh issue create --assignee`), у тексті її не дублюй.
3. **Паралельність.** Розбий роботу так, щоб її можна було вести одночасно. Блокуючі issues мають бути малими й першими, решта працюють із контрактів і моків. Для кожного вказуй залежності.
4. **Самодостатність.** Кожен issue містить: назву, мітки, контекст, що зробити (за шарами й файлами), які історії та критерії покриває, посилання на конкретні розділи документів, перелік тестів із ID критеріїв, умови готовності. Ніхто не повинна відкривати інші issues, щоб зрозуміти свій.
5. **Джерела правди.** Назви, поля, статуси, коди помилок бери з наявних контрактів. Нічого не вигадуй. Відкриті питання не закривай мовчки: виноси їх у специфікацію як пропозиції, що потребують погодження.
6. **Специфікація обсягу.** Якщо потрібна, окремий короткий документ, що не дублює контракти: межі обсягу, рішення за відкритими питаннями, зв'язка «екран → ендпоінт → критерій → issue», наскрізні критерії приймання.
7. **Загальні вимоги.** Окремий блок у кінці кожного issue: гілка й PR за правилами `AGENTS.md`, `Closes #N`, локальні перевірки, власні промпти, ШІ-рев'ю власного PR, тести з ID критерію.
8. **CI і ШІ-рев'ю.** Окремий issue на перевірки для кожного PR і ШІ-рев'ю агента. Секрети додає власник репозиторію вручну.
9. **Фінальний issue.** Фінальний PR, ШІ-рев'ю всього diff, виправлення, мердж після зеленого CI.
10. **Без термінів.** У текстах issues не пиши дат і термінів.

### Створення й перевірка

Створи issues через `gh issue create` у порядку залежностей: мітки, milestone, виконавиці, тіло з файлу. Після створення перевір, що номери збігаються з посиланнями `#N` у текстах, що виконавиці призначені, що тіла непорожні й не містять дат.

### Формат відповіді

Українською. Спершу висновок про межі обсягу й ризики. Далі список створених або оновлених issues, підсумкова таблиця «учасниця → issues» і розбіжності між завданням і контрактами. Не стверджуй, що реалізовано те, чого немає; припущення позначай.
