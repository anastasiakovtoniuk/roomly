# Виконання issue: мета-промпт

Універсальний промпт: кожна учасниця дає його своєму ШІ-асистентові, підставивши номер issue.

## Промпт

Виконай GitHub issue №<N> у цьому репозиторії. Працюй за порядком нижче й не пропускай кроків.

### 1. Контекст

1. Прочитай issue: `gh issue view <N>`. Це єдине джерело завдання, нічого поза ним не додавай.
2. Прочитай `AGENTS.md` і `CLAUDE.md`: інваріанти, заборони, команди перевірок, правила Git-процесу.
3. Прочитай документи, на які посилається issue (специфікації, контракти, ADR, критерії приймання).
4. Прочитай код, який змінюватимеш, і найближчий наявний тест як зразок. Перевір `git status` і `git log -5`.
5. Якщо issue залежить від іншого, якого ще немає в цільовій гілці, працюй за контрактом або моками, нічого не вигадуючи, і зазнач це в описі PR.

### 2. План

Коротко (5–8 пунктів) запиши файли, які змінюватимеш, і тести, які додаси. Вкажи історії, AC та правила, яких торкається зміна. Якщо issue суперечить контрактам чи іншому джерелу правди, не вирішуй мовчки: опиши розбіжність і запитай.

### 3. Реалізація

1. Створи гілку за правилами з `AGENTS.md`, від гілки, яку вказано в issue.
2. Роби мінімальну зміну лише для цього issue. Дотримуйся наявної архітектури, структури й стилю модуля.
3. Не вигадуй сутності, поля, ендпоінти, значення enum, коди помилок: бери їх із контрактів і спільного коду. Не довіряй клієнтським даним про роль чи власника. Не приховуй помилки типів. Секрети не комітити.
4. Пиши тести разом з кодом, назви з ID критерію з issue. Те, що має гарантувати сховище, перевіряй на реальній БД, а не моками.
5. Коміти дрібні, з префіксами за правилами репозиторію.

### 4. Перевірки перед PR

Запусти команди перевірок, вказані в `AGENTS.md` (лінтер, форматування, типи, тести, збірка). Виправляй помилки, не послаблюючи перевірки й не видаляючи тести. Не стверджуй, що перевірка пройшла, якщо ти її не запускала. Для змін інтерфейсу перевір результат у браузері.

### 5. Промпти

Збережи ключові промпти цього сеансу в папці `prompts/` за правилами, зазначеними в issue: генерацію коду й виправлення помилок окремо, у секції зі своїм ім'ям.

### 6. Pull Request і рев'ю

1. Відкрий PR у гілку, вказану в issue, із `Closes #<N>`, переліком змін, історій і AC та результатом перевірок.
2. Запусти ШІ-рев'ю власного diff (`/code-review`; для змін авторизації чи доступу до даних ще `/security-review`). Додай знахідки коментарем у PR, виправ суттєві, запиши результат у файл промптів рев'ю.

### 7. Підсумок

Українською вкажи: які файли й поведінку змінено, які команди виконано та результат, що не перевірено й чому, які відкриті питання впливають на готовність.
