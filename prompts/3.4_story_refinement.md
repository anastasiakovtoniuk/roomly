# Промпт для уточнення та декомпозиції історій MVP (Story Refinement)

Ти — досвідчений Product Manager і бізнес-аналітик, який працює з методологією User Story Mapping (Jeff Patton).

## Вхідні дані

До запиту додано файли:

- `docs/project_context.md` — контекст продукту, ролі, ключова механіка, обмеження команди та правила оформлення. Дотримуйся їх.
- `results/3.3_story_mapping_scope_result.md` — межі MVP. Бери з нього **лише ID** історій з розділу «In Scope (MVP)». Повних формулювань там немає, лише короткі назви.
- `results/3.2_story_drafts_result.md` — пул драфтів. Бери з нього **повні формулювання** («Як… я хочу… щоб…»), джерела й типи для ID, відібраних у 3.3. Історії, яких немає в In Scope, ігноруй.
- `results/3.1_user_journey_result.md` — головний шлях користувача (Happy Path).
- `results/2.2_vpc_result.md` — Jobs, Pains і Gains ключової персони.
- `results/2.3_critical_analysis_result.md` — ризики та висновки щодо концепції.

## Завдання

Доопрацюй кожну історію In Scope (MVP) і розглядай її окремо:

1. **Перевір за канонічною тричастинною формулою:** «Як [хто], я хочу [що], щоб [навіщо / цінність]».
2. **Перевір на атомарність.** Якщо в історії змішано дві різні дії (наприклад, «створювати й редагувати», «згенерувати й роздрукувати», «бачити помилку й повторити дію»), розділи її на дві незалежні історії (декомпозиція).

Не змінюй межі MVP: не додавай нових історій, яких немає в In Scope, не повертай історії з Out of Scope й не вилучай історії з In Scope.

## Критерії перевірки формули

1. **Хто.** Лише роль «Студент» або «Адміністратор», як у `project_context.md`. Ситуацію студента передавай у тексті: «Як студент, який забронював кімнату…», «Як студент із групи…», «Як студент, що шукає кімнату…». Не вигадуй окремих ролей.
2. **Що.** Одна конкретна дія користувача, яку можна показати в застосунку. Без деталей реалізації та UI («екран», «кнопка», «в один дотик», «вкладка»), без числових вимог до швидкості («за хвилину»).
3. **Навіщо.** Реальна користь для того, хто виконує дію. Вона не повторює частину «що» іншими словами й не посилається на функціонал, якого немає в MVP (наприклад, на санкції, ліміти, SSO, push-сповіщення). Якщо цінність у драфті суперечить межам MVP, переформулюй її через Pain, Gain чи Job з VPC.

## Критерії якості й вимірюваності (INVEST)

Кожна фінальна історія має відповідати класичним вимогам до користувацьких історій:

1. **Вимірювана й перевірювана (Testable).** За формулюванням можна написати тест: результат дії спостережний (з'являється, змінює статус, зберігається, недоступний іншим), а величини задані конкретно (24 години, весь grace period, статус «підтверджене»).
2. **Без невизначених слів.** Не використовуй слів, які неможливо виміряти чи перевірити: «швидко», «одразу», «зручно», «зрозуміло», «актуально», «кілька», «зайвий», «якісно», «легко», «просто». Заміни їх спостережним результатом або конкретним параметром. Якщо значення параметра не визначено в документах, познач відкрите питання, а не вигадуй число.
3. **Цінність спостережна (Valuable).** Частина «щоб» описує реальний результат для користувача, який можна перевірити (наприклад, «бронювання отримало статус "підтверджене"», «слот став доступним для інших»), а не загальне побажання («щоб контролювати плани», «щоб допомогти»).
4. **Незалежна (Independent).** Історію можна реалізувати й перевірити окремо. Якщо вона залежить від іншої, зазнач залежність у колонці «Проблема».
5. **Обговорювана (Negotiable).** Формулювання не диктує реалізацію й вигляд інтерфейсу.
6. **Оцінювана й невелика (Estimable, Small).** Історія настільки конкретна й мала, що команда оцінює її й реалізує за одну ітерацію.

Параметри, які вже визначені командою, використовуй у формулюваннях без змін. Параметр-гіпотезу познач у колонці «Проблема» як **[Гіпотеза]**.

## Критерії атомарності

1. Одна історія — одна дія користувача й одна цінність.
2. Історію потрібно розділити, якщо у формулюванні є дві дії, з'єднані сполучником «і», комою чи словом «та», і кожну можна реалізувати й перевірити окремо.
3. Не дроби історію, якщо це один потік з однією цінністю (наприклад, вибір дати й показ слотів на цю дату — це одна дія «переглянути слоти на дату»).
4. Кожна нова історія має зберігати власну цінність. Не створюй історій без «щоб».

## Правила

- Зберігай ID оригіналу. Якщо історію розділено, додай до ID літерні суфікси: `US-3.2` → `US-3.2a`, `US-3.2b`. Не перенумеровуй інші історії.
- Для кожної історії вкажи статус: «не змінено», «уточнено» (формулювання виправлено, історія лишилася однією) або «розділено» (історію розбито на кілька незалежних; кожна нова історія отримує власний рядок і ID).
- Не дублюй текст. Для неуточнених історій нове формулювання не наводь.
- Вимоги до швидкості, UI та інші обмеження, які ти прибираєш із формулювання, не втрачай: зазнач їх у колонці «Проблема» як винесені вимоги.
- Не вигадуй факти. Розрізняй [Факт від команди], [Потребує перевірки] і [Гіпотеза]. Те, чого не визначено в документах (наприклад, час нагадування), познач як відкрите питання, а не вигадуй значення.
- Пиши українською, лаконічно, без маркетингових формулювань.

## Формат відповіді

1. **Підсумок** — скільки історій було, скільки не змінено, уточнено та розділено (і на скільки нових історій), скільки стало.
2. **Таблиця історій MVP** — одна таблиця `| ID | Крок | Початкове формулювання | Проблема | Статус |`, впорядкована за кроками User Journey, далі «Наскрізне» та «Адміністрування».
    - **Крок** — крок User Journey, «Наскрізне» або «Адміністрування», як у пулі 3.2 (для розділених історій крок оригіналу).
    - **Початкове формулювання** — повний текст історії з 3.2. Для другої й наступних історій після розділення напиши «те саме, що в <ID першої>».
    - **Проблема** — що саме не так у початковому формулюванні (порушення формули, змішані дії, деталь UI, цінність поза межами MVP тощо). Якщо ти прибираєш із формулювання вимогу чи обмеження, зазнач, яку саме винесено. Для неуточнених історій став «—». Для другої й наступних історій після розділення дублюй посилання «те саме, що в <ID першої>».
    - **Статус** — «не змінено», «уточнено: <нове формулювання>» або «розділено: <нове формулювання цієї історії>». Нове формулювання наводь лише для уточнених і розділених історій. Роль окремою колонкою не виводь: вона є в тексті історії.
3. **Перевірка** — кількісна звірка: кожен оригінальний ID In Scope представлений рівно в одному рядку (або в кількох, якщо розділено), загальна кількість історій збігається з підсумком.
4. **Відкриті питання й припущення** — що треба уточнити в команди. З позначками [Факт від команди] / [Потребує перевірки] / [Гіпотеза].

## Перевірка перед відповіддю

- Кількість оригінальних історій дорівнює кількості історій In Scope у `3.3_story_mapping_scope_result.md`.
- У жодній фінальній історії немає двох незалежних дій.
- У кожній фінальній історії є всі три частини формули, а цінність не повторює дію.
- У жодній фінальній історії немає невизначених слів із переліку (розділ «Критерії якості й вимірюваності») і для кожної можна сформулювати перевірку «так / ні».
- Жодна історія не посилається на функціонал, що в Out of Scope.
