### Issue #2: PR-шаблон і заготовки промптів

**Промпт** (структурований; базується на [issue_execution.md](issue_execution.md)):

- **Завдання:** виконати GitHub issue №2.
- **Порядок роботи:**

  2. План: файли, тести, історії, правила; розбіжності з джерелами описати й запитати.

  5. Промпти: зберегти у своїй секції `prompts/`.
  6. Перегляд перед публікацією: зупинитися, показати підсумок, чекати «так».
  7. Pull Request і ШІ-рев'ю до публікації; мердж лише за командою.
  8. Підсумок українською.

### Issue #3: CI на кожен PR і ШІ-рев'ю агент

**Промпт** (структурований; базується на [issue_execution.md](issue_execution.md)):

- **Завдання:** виконати GitHub issue №3.
- **Порядок роботи:** контекст, план у режимі планування з погодженням, реалізація в гілці від `feature/booking-flow`, перевірки, промпти, перегляд перед публікацією, PR і рев'ю від CI, підсумок.
- **Обмеження:** токен робочого акаунта асистентові не передається; секрет додає власниця репозиторію. До «так» нічого не публікувати.
- **Уточнення в діалозі:** «я отримала токен, але не автор репо й не можу додати секрет; чи можна перевірити, що CI працює?» Асистент відмовився брати токен у чат і запропонував перевірку у власному форку з секретом, доданим самостійно через `gh secret set`.

**Результат:**

1. Асистент перевірив, що `ci.yml` уже запускається на `pull_request` у будь-яку гілку з усіма кроками, і не змінював його.
2. Створив `.github/workflows/ai-review.yml`: `claude-code-action@v1` з `claude_code_oauth_token`, права `contents: read`, `pull-requests: write`, `id-token: write`, інструменти лише `Read`, `Glob`, `Grep`, `gh pr diff/view/comment`; пропуск PR із форків і пропуск із попередженням без секрету; скасування застарілого рев'ю на новий push.
3. Заповнив «Спільні правила аудиту» в [5.3](5.3_ai_code_review.md): архітектура, безпека (BR-8, BR-17, FB-12), помилки, цілісність (BR-1), контракти, чистота коду, межі MVP і формат коментаря.
4. Додав розділ «CI і ШІ-рев'ю» в `README.md` і рядок workflow у таблицю структури `AGENTS.md`.

### Issue #4: Zod і спільні схеми сценарію в `shared/`

**Промпт** (структурований; базується на [issue_execution.md](issue_execution.md)):

- **Завдання:** виконати GitHub issue №4.
- **Порядок роботи:** контекст (issue, `AGENTS.md`, `CLAUDE.md`, `api_spec.md` §1–2, §5–7, §11, `error_format.md`, `data_model.md`, `booking_flow.md`, наявні `shared/`, `appError`, `errorHandler`, `health.test.ts`), план, реалізація, перевірки, збереження промптів, перегляд перед публікацією, Pull Request і рев'ю, підсумок.
- **Обмеження:** мінімальна зміна лише для цього issue; схеми, поля й коди лише з контрактів; розбіжності з джерелами описати й запитати; до явного «так» нічого не публікувати.
- **Рішення за запитанням асистента:** у `details.fields[].reason` записувати коди Zod 4 без змін, а приклад у `error_format.md` виправити в цьому ж PR.

**Результат:**

1. Асистент знайшов дві розбіжності: (а) приклад `reason` в `error_format.md` (`invalid_email`, `too_short`) не збігається з кодами Zod 4; (б) межа пароля 72 у контракті задана в символах, а bcrypt рахує байти. Пункт (а) вирішено запитанням, (б) реалізовано за контрактом і відзначено в PR.
2. Додано `zod@4.6.7` у `shared` і `server`; інші залежності не змінено.
3. Створено `shared/src/schemas.ts` (сім схем з `api_spec.md` §11 для сценарію) і `shared/src/api.ts` (типи `User`, `Room`, `Slot`, `AvailableSlot`, `Booking` і тіла відповідей `register`/`login`/`me`, списків кімнат, вільних слотів, бронювань). Константи вже були в `domain.ts`.
4. Створено `server/src/middleware/validate.ts`: перевіряє `params`, `query` і `body`, збирає всі помилки в один `VALIDATION_ERROR` з `details.fields`, а обробнику передає нормалізовані дані.
5. Додано тести `server/test/schemas.test.ts` і `server/test/validate.test.ts` (21 тест), назви починаються з ID критеріїв.

### Issue #5: автентифікація — реєстрація, вхід, вихід, сесії

**Промпт** (структурований; базується на [issue_execution.md](issue_execution.md)):

- **Завдання:** виконати GitHub issue №5.
- **Порядок роботи:** контекст (issue, `AGENTS.md`, `CLAUDE.md`, `api_spec.md` §1–3, §5, §11, `data_model.md` §3.1, §3.5, `error_format.md`, ADR-0005, критерії US-1.2, US-X.1a, US-X.1b, SYS-AC-08 у результаті 3.5, наявні `shared/`, `app.ts`, `validate.ts`, `errorHandler.ts`, seed, `health.test.ts`, `validate.test.ts`), план, реалізація, перевірки, збереження промптів, перегляд перед публікацією, Pull Request і рев'ю, підсумок.
- **Обмеження:** мінімальна зміна лише для цього issue; поля, коди й cookie лише з контрактів і `shared/`; ідентифікатор і роль лише із сесії; розбіжності описати й запитати; до явного «так» нічого не публікувати.
- **Рішення за запитанням асистента:** запит зі зміною даних без `Content-Type: application/json` повертає `400 VALIDATION_ERROR` з `details.fields: [{ path: "body", reason: "invalid_content_type" }]`; нову причину дописано в `error_format.md` §1 у цьому ж PR, нового коду помилки немає.

**Результат:**

1. Асистент знайшов розбіжність: контракт вимагає JSON для змін даних, але не визначає відповідь на інший `Content-Type`. Вирішено запитанням (див. вище).
2. Створено модуль `server/src/modules/auth/`: `session.ts` (випадковий токен 32 байти, у БД лише SHA-256, cookie `roomly_session` з `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` при HTTPS, без строку дії; розбір заголовка Cookie без нової залежності), `auth.service.ts` (реєстрація з bcryptjs і роллю `student`, `EMAIL_ALREADY_REGISTERED` також при паралельній реєстрації через унікальний індекс; вхід з однаковою відповіддю `INVALID_CREDENTIALS` і порівнянням із фіктивним хешем для неіснуючої пошти; вихід; пошук користувача сесії), `auth.router.ts` (`register` 201, `login` 200, `logout` 204, `me`).
3. Рішення асистента: при вході чи реєстрації стара сесія з cookie цього пристрою видаляється з бази, а не лише перезаписується cookie (US-X.1b-AC-03).
4. Створено `server/src/middleware/auth.ts` (`requireAuth`, `requireRole`, `getAuthUser`; `req.authUser` через module augmentation Express) і `server/src/middleware/requireJson.ts`; обидва роутери підключено в `app.ts`.
5. Додано `server/test/auth.test.ts` (19 тестів; після ШІ-рев'ю — 20, див. 5.3): US-1.2-AC-01…03, US-X.1a-AC-01…02, US-X.1b-AC-01…03, SYS-AC-08, `UNAUTHENTICATED`, `Content-Type`, наскрізний цикл реєстрація → me → logout → login. Студентський і адміністративний доступ перевірено на тестових маршрутах із тими самими middleware, бо ендпоінтів бронювань і адміністрування ще немає.
6. Оновлено `AGENTS.md`: модуль `auth/`, нові middleware, стан реалізації.
