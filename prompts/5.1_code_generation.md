# 5.1 Генерація коду

Запити, за якими ШІ-асистенти в IDE чи CLI генерували код і документи сценарію. Кожна учасниця заповнює лише свою секцію: issue, використаний промпт, що саме згенеровано.

## Малій Олександра

### Issue #1: специфікація сценарію «Бронювання слота студентом»

**Промпт** (структурований; базується на [issue_execution.md](issue_execution.md)):

- **Завдання:** виконати GitHub issue №1.
- **Порядок роботи:** контекст (issue, `AGENTS.md`, `CLAUDE.md`, документи з посилань), план, реалізація, перевірки, збереження промптів, Pull Request і рев'ю, підсумок.
- **Обмеження:** мінімальна зміна лише для цього issue; нічого поза контрактами; розбіжності з джерелами описати й запитати.

**Результат:**

1. Асистент прочитав issue #1, `AGENTS.md`, `CLAUDE.md`, контракти `docs/contracts/` і критерії `results/3.5_acceptance_criteria_result.md`; звірив ID критеріїв та відкриті питання Q04, Q07, Q08, Q12.
2. Виявив три розбіжності між issue і джерелами (US-4.2-AC-01 і Q12, US-4.3-AC-01 і Q07, автоскасування за SYS-AC-02) і не вирішив їх мовчки, а зафіксував як `[Пропозиція, потребує погодження]`.
3. Створив `docs/scenarios/booking_flow.md` (межі, рішення, зв'язка «екран → ендпоінт → AC → issue», демо-дані, вісім Gherkin-сценаріїв) і додав посилання в `AGENTS.md` та `README.md`.

### Issue #2: PR-шаблон і заготовки промптів

**Промпт** (структурований; базується на [issue_execution.md](issue_execution.md)):

- **Завдання:** виконати GitHub issue №2.
- **Порядок роботи:**
  1. Контекст: issue, `AGENTS.md`, `CLAUDE.md`, документи з посилань, код і `git status`.
  2. План: файли, тести, історії, правила; розбіжності з джерелами описати й запитати.
  3. Реалізація: гілка за `AGENTS.md`, мінімальна зміна, нічого поза контрактами; для документації один фінальний коміт.
  4. Перевірки: lint, форматування, типи, тести, збірка; не стверджувати непройдене.
  5. Промпти: зберегти у своїй секції `prompts/`.
  6. Перегляд перед публікацією: зупинитися, показати підсумок, чекати «так».
  7. Pull Request і ШІ-рев'ю до публікації; мердж лише за командою.
  8. Підсумок українською.
- **Обмеження:** до «так» нічого не публікувати (push, PR, коментарі); PR самостійно не зливати.
- **Додаткові вказівки після перегляду:** опублікувати зміни; переписати відкритий PR за новим шаблоном; розв'язати конфлікт у `prompts/`, віддавши перевагу пізнішим промптам; повідомити, чи впливають зміни на відкритий PR для issue #1 (PR #16); записати промпт у структурованому вигляді.

**Результат:** асистент синхронізував локально `feature/booking-flow` з `main`, створив `.github/pull_request_template.md`, три файли `prompts/5.1`–`5.3` із секціями на п'ятьох учасниць і уточнив в `AGENTS.md` посилання на шаблон. Захист `main` не налаштовував: потрібні права адміністратора репозиторію.

### Issue #3: CI на кожен PR і ШІ-рев'ю агент

**Промпт** (структурований; базується на [issue_execution.md](issue_execution.md)):

- **Завдання:** виконати GitHub issue №3.
- **Порядок роботи:** контекст, план у режимі планування з погодженням, реалізація в гілці від `feature/booking-flow`, перевірки, промпти, перегляд перед публікацією, PR і рев'ю від CI, підсумок.
- **Обмеження:** токен робочого акаунта асистентові не передається; секрет додає власниця репозиторію. До «так» нічого не публікувати.
- **Уточнення в діалозі:** «я отримала токен, але не автор репо й не можу додати секрет; чи можна перевірити, що CI працює?» Асистент відмовився брати токен у чат і запропонував перевірку у власному форку з секретом, доданим самостійно через `gh secret set`.

**Результат:**

1. Асистент перевірив, що `ci.yml` уже запускається на `pull_request` у будь-яку гілку з усіма кроками, і не змінював його.
2. Створив `.github/workflows/ai-review.yml`: `claude-code-action@v1` з `claude_code_oauth_token`, права `contents: read`, `pull-requests: write`, `id-token: write`, інструменти лише `Read`, `Glob`, `Grep`, `gh pr diff/view/comment`; пропуск PR із форків і пропуск із попередженням без секрету; скасування застарілого рев'ю на новий push.
3. Заповнив «Спільні правила аудиту» в [5.3](5.3_ai_code_review.md): архітектура, безпека (BR-8, BR-17, FB-12), помилки, цілісність (BR-1), контракти, чистота коду, межі MVP і формат коментаря.
4. Додав розділ «CI і ШІ-рев'ю» в `README.md` і рядок workflow у таблицю структури `AGENTS.md`.
