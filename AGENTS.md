# AGENTS.md — Roomly

Інструкції для мовних моделей та AI-асистентів, які працюють із цим репозиторієм. Розмістити файл у корені репозиторію; він стосується всіх його папок.

**Звірено:** 30.10.2026, гілка `main`, після створення Walking Skeleton (крок 4.4).
Перед роботою перевір актуальний стан файлів: цей документ не замінює вимоги, контракти та конфігурацію проєкту.

## 1. Суть проєкту

Roomly допомагає студентам бронювати навчальні кімнати для групової роботи. Якщо присутність не підтверджена QR-кодом протягом визначеного періоду після початку бронювання, система автоскасовує бронювання та звільняє слот.

Ролі: **студент** і **адміністратор**. Адміністратор керує кімнатами, створює слоти, генерує та друкує QR, переглядає бронювання, виконує ручне підтвердження і скасування.

У MVP — **31 фінальна User Story**. Новий опис клієнта в ADR-0002 визначає **мобільний вебзастосунок у браузері телефона**. Згадки про магазин застосунків у ранньому User Journey не є підставою створювати нативні iOS/Android-клієнти.

## 2. Поточний стан і джерела істини

Репозиторій містить документацію, технічні контракти (`docs/contracts/`) і **Walking Skeleton без бізнес-логіки**: npm workspaces, сервер з `GET /api/health` і єдиним обробником помилок, схему Prisma й першу міграцію за контрактом, seed адміністратора, клієнт-заглушку, тести, лінтер, форматер і CI. **Жодну User Story ще не реалізовано.** Усі **ADR-0001…ADR-0008 мають статус «Запропоновано»**.

Перед змінами прочитай:

1. [docs/requirements.md](docs/requirements.md) — основна специфікація: Scope, фінальні історії, Acceptance Criteria, відкриті питання.
2. [docs/project_context.md](docs/project_context.md) — короткий контекст і явні рішення команди.
3. Релевантні [docs/adr/](docs/adr/) — архітектура; обов’язково перевір статус кожного ADR.
4. [docs/requirements_digest.md](docs/requirements_digest.md) — бізнес-правила BR, заборони FB, припущення TA і прогалини G.
5. [results/3.5_acceptance_criteria_result.md](results/3.5_acceptance_criteria_result.md) — докладні критерії та Gherkin; [results/3.4_story_refinement_result.md](results/3.4_story_refinement_result.md) — фінальні формулювання історій.
6. Наявні технічні контракти в `docs/`, конфігурації, код і тести конкретного модуля.

**Правила пріоритету:**

- Явне актуальне рішення команди переважає ранню рекомендацію чи гіпотезу.
- Для бізнес-поведінки звіряй фінальні історії та AC; для реалізації — погоджені контракти й прийняті ADR.
- `[Пропозиція]`, `[Технічне припущення]`, `[Гіпотеза]` та «Запропоновано» не означають затвердження. Не змінюй ці позначки самостійно.
- Дайджести використовуй як навігацію до джерел. Зокрема, твердження G11 у `requirements_digest.md` про відсутність AC застаріле: AC уже є в `requirements.md` та результаті 3.5.
- «Пропозиція за замовчуванням» у G1…G10 не закриває питання команди. Зокрема, не підміняй нагадування **за 24 години** правилом **у будь-який момент протягом найближчих 24 годин** без погодження Q05/G10. Не вирішуй самостійно суперечність між кінцевим статусом «підтверджене» (BR-9) і його можливим скасуванням адміністратором (BR-7, Q18/G2).
- Не вирішуй суперечність за датою файла автоматично. Покажи конкретні розбіжні правила та продовжуй частини роботи, які від них не залежать.

**Не вигадуй поля сутностей самостійно — перевіряй контракти в `docs/`.**
Контракти: [docs/contracts/data_model.md](docs/contracts/data_model.md) (таблиці, поля, обмеження), [docs/contracts/api_spec.md](docs/contracts/api_spec.md) (ендпоінти, тіла, відповіді, статус-коди), [docs/contracts/error_format.md](docs/contracts/error_format.md) (тіло помилки й 18 кодів). Значення статусів, ролей і кодів помилок у коді беруться лише з `shared/`. Позначки **[Пропозиція]** у контрактах — ще не затверджені командою; місця, що залежать від G/Q, описані в самих контрактах. Якщо потрібного поля, коду чи ендпоінта в контракті немає, спершу онови контракт, потім код.

### Збірка, запуск і тестування

Усі команди — з кореня репозиторію.

| Дія | Команда | Що робить |
| --- | --- | --- |
| Установлення залежностей | `npm install` | Ставить пакети всіх workspaces і генерує клієнт Prisma (`postinstall`) |
| Локальний запуск | `npm run dev` | `.env` з шаблону, якщо його немає → `prisma migrate deploy` → seed адміністратора → сервер (`:3000`) і клієнт (`:5173`) через concurrently |
| Збірка | `npm run build` | `typecheck` і `vite build` клієнта |

`npm run dev` застосовує лише **наявні** міграції й не скидає базу. Порти й параметри — змінні `SERVER_PORT`, `CLIENT_PORT`, `DATABASE_URL`, `APP_TIMEZONE`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_NAME` у `.env`; нових змінних не вигадуй без оновлення `.env.example` і README. Сервер у dev запускається через `node --watch --import tsx`, бо `tsx watch` під concurrently на Windows не стартує.

Перед завершенням зміни коду запускай `npm run lint`, `npm run typecheck` і `npm test`.

Для перевірки документаційних змін у локальному клоні доступні звичайні Git-команди:

```bash
git status --short
git diff --check
git diff --stat
```

Це перевірка змін, а не збірка чи функціональні тести. Пошук файлів і правил: `rg --files`, `rg -n "US-3.4|SYS-AC-06|BR-1" docs results`.

## 5. Правила кодогенерації

1. **Починай з вимоги.** Визнач ID історії, AC та релевантні BR/FB. Прочитай файли, які змінюватимеш, і перевір `git status`.
2. **Роби мінімальну зміну для завдання.** Зберігай стиль та структуру модуля. Не додавай сторонніх рефакторингів, залежностей чи функцій.
3. **Контракт перед реалізацією.** Використовуй фактичні типи й схеми. Не дублюй статуси, валідацію та коди помилок із `shared/` у клієнті й сервері.
4. **Дотримуйся запропонованого поділу після погодження ADR:** роутер обробляє HTTP, сервіс — бізнес-правила, ORM — доступ до даних. Не перенось доменну логіку в UI або великі обробники маршрутів.
5. **Строгі типи.** Не приховуй помилки через необґрунтовані `any`, `as any`, `@ts-ignore` чи вимкнення strict. Перевіряй зовнішні дані на сервері навіть за наявності клієнтської валідації.
6. **Єдине джерело часу.** За ADR-0003/0006 сервіси отримують час через підмінюване джерело; часові правила зосереджуються в одному місці. Клієнт показує дедлайн і відлік за даними сервера.
7. **Явні помилки.** Використовуй погоджений формат і машинні коди. Не приховуй винятки й не показуй успіх без підтвердженого результату. Відсутність мережі до запиту та втрата відповіді після можливого збереження — різні випадки.
8. **Конфігурація без секретів.** Пароль адміністратора надходить із середовища. У шаблонах — лише безпечні приклади або порожні значення; наявний `.env` не перезаписуй.
9. **Узгоджені зміни.** Якщо завдання змінює контракт, онови пов’язані схеми, клієнт, сервер, документацію й тести. Для `shared/` ADR-0001 пропонує рев’ю з боку клієнта й сервера.
10. **Мова.** Пояснення й документація — українською. Ідентифікатори коду — за конвенціями проєкту. Коментарі пояснюють причину рішення.
11. **Фіксуй обмеження.** Якщо нез’ясоване правило впливає на результат, назви питання G/Q і залежну частину роботи. Продовжуй незалежні частини; не закривай прогалину мовчазною здогадкою.

## 6. Інваріанти Roomly

- Один слот одночасно має не більше одного живого бронювання: «активне» або «підтверджене». Захист має працювати при паралельних запитах і на рівні сховища.
- Студент бачить свої бронювання й скасовує власне активне бронювання. Адміністративні права перевіряються на сервері.
- QR ідентифікує кімнату. Підтвердити присутність може будь-який авторизований студент; власність бронювання та членство в групі не є умовами QR-check-in.
- Успішне підтвердження не змінює власника бронювання. Право сканувати QR не дає права читати особисті деталі чи скасовувати чужі записи.
- Автоскасування виконується сервером і не залежить від відкритого клієнта. Підтверджені та вже скасовані записи воно не переписує.
- Конкурентні переходи статусу виконуються умовно, за поточним станом. Повторне підтвердження не створює нового бронювання; скасований запис не відновлюється.
- Єдиний grace period — рішення команди; **15 хвилин — гіпотеза**. Дедлайн повторного бронювання залишку слота, точні межі часу й пріоритет конкурентних дій потребують окремого рішення.
- Повідомлення US-5.4 показується на початку бронювання у застосунку. Нагадування за 24 години — гіпотеза; push не входить до MVP.
- Документовані статуси: «активне», «підтверджене», «скасоване студентом», «автоскасоване». Назви значень enum не вигадуй; п’ятий статус і адміністративне скасування підтвердженого запису ще потребують погодження.

## 7. Чіткі інженерні заборони

- **Не вигадуй поля, сутності, ендпоінти, enum-значення, HTTP-коди та формати помилок.** Перевір `docs/` і наявні контракти; нове контрактне рішення явно погоджуй.
- **Не видавай заплановане за реалізоване:** папки, npm-скрипти, health endpoint, CI, тести та ADR зі статусом «Запропоновано».
- **Не розширюй MVP без завдання:** групи й запрошення, push, SSO, оплати, чат, санкції, ліміти, черги, аналітика, продовження/перенесення, дострокове завершення, відновлення бронювання, динамічний QR.
- **Не додавай редагування чи видалення слотів за однією згадкою в контексті.** Фінальна US-A.2 описує створення; суперечність — Q17/G6.
- **Не довіряй ролі, власнику бронювання або ідентифікатору поточного користувача з клієнтського запиту.** Встановлюй їх через серверну автентифікацію. Прихований адмін-екран не замінює перевірку прав.
- **Не зберігай паролі відкритим текстом і не віддавай секрети сесій або QR-токени в загальних відповідях для студентів.** Сканування передає прочитаний токен на перевірку; публікація токена в каталозі кімнат не потрібна.
- **Не захищай бронювання лише послідовністю «перевірити вільність → вставити запис».** Потрібне обмеження цілісності, яке витримує конкурентність.
- **Не використовуй клієнтський годинник, таймер або надісланий клієнтом статус як підставу для переходу бронювання.**
- **Для варіанта Prisma з ADR-0004:** не застосовуй `prisma db push`; не дописуй захисний частковий індекс вручну лише в SQL міграції — він має бути відображений у схемі через погоджений механізм. Не оновлюй Prisma без перевірки міграцій і збереження захисту BR-1.
- **Не стирай історію бронювань, не додавай каскадне видалення й не скидай БД для проходження тесту.** Тестова база має бути відокремлена від робочих даних.
- **Не обходь перевірки:** не видаляй тести, не послаблюй твердження, не вимикай лінтер або перевірку типів заради зеленого результату.
- **Не коміть секрети, локальні бази, `.env`, сертифікати та приватні ключі.** Не виводь їх у логи чи відповіді.
- **Не перезаписуй чужі незакомічені зміни, не використовуй `git reset --hard`, примусовий push або руйнівні міграції без прямого дозволу.**
- **Не стверджуй, що тести пройдено, якщо вони не запускалися.** Gherkin у Markdown — специфікація, а не виконаний автоматичний тест.

## 8. Перевірка результату

Тести пиши за ADR-0008 у `server/test/` за зразком `health.test.ts`; час підмінюй через `setClock`. Назви тестів починай з ID критерію. Пріоритет перевірок:

1. **SYS-AC-06 / US-3.4:** паралельне бронювання одного слота; сховище відхиляє другий живий запис.
2. **SYS-AC-02…05, SYS-AC-07, SYS-AC-10:** переходи статусів, автоскасування, конкурентність і звільнення слота.
3. **US-5.1, US-5.6b:** невідомий QR, відсутнє бронювання, повтор, скасований запис, мережеві помилки.
4. **SYS-AC-08…09 / US-X.1a / US-4.3:** seed адміністратора, захист ролей і власних даних.
5. Релевантні часові випадки з визначеним результатом; час підмінюй у тестах без реального очікування.

Інтеграційні тести запропоновано виконувати через Vitest + Supertest на окремій SQLite-базі, створеній міграціями. Не підмінюй перевірку обмеження БД лише моками. Для документаційної правки достатньо перевірки змісту, посилань і diff.

Камеру на iOS Safari / Android Chrome, друк і зчитування QR з паперу, таймер та повідомлення перевіряй вручну відповідно до ADR-0008. Для камери телефона потрібен перевірений захищений контекст; HTTP за IP ноутбука не прирівнюй до `localhost`. Не гарантуй роботу самопідписаного сертифіката без перевірки на цільовому пристрої.

Не додавай очікуваний результат для рівно 14:15, нового дедлайну залишку слота чи адміністративного статусу, поки відповідне питання не вирішене. Такі перевірки явно позначай як залежні від рішення, а не як пройдені.
